1. 큰 그림 — 두 저장소가 하는 일
═══════════════════════════════════════════════════════════

VnTool(java-start, C#/.NET 10/Avalonia)은 비주얼노벨 저작 도구다.
작가가 대사·조건·선택지·연출을 만들면 .yarn과 CSV를 산출하고,
그것을 ked-presentation-runtime(이 저장소, 유니티)이 재생한다.

VnTool은 저작 도구로서는 1차 완성 상태다 — 대사 편집, 조건·선택지,
연출 커맨드 편집, 라이브 출력, 무대 프리뷰까지 돌아가고 테스트 487개가 붙들고 있다.

지금 하려는 다음 단계가 Phase 2b: "정지 프레임 렌더러".
작가가 툴 안에서 **완성된 게임 화면과 같은 구도**를 미리 보는 것이다.
지금은 근사만 보여 준다 — 슬롯을 화면 아래에 균등 나열할 뿐 실제 좌표를 모른다.

═══════════════════════════════════════════════════════════
2. 왜 런타임부터 고치는가 (이게 핵심이다)
═══════════════════════════════════════════════════════════

VnTool이 실제 구도를 그리려면 "커맨드 열 → 확정된 무대 상태"를 계산해야 한다.
그 계산은 이미 이 저장소에 있다. 커맨드 201종이 무엇을 어디에 놓는지 아는 것은 런타임뿐이다.

선택지는 셋이었다:
  ① 런타임에서 순수 코어를 뽑아 VnTool이 참조해 같이 쓴다
  ② VnTool이 따로 구현하고 교차 검증한다
  ③ 런타임이 상태를 덤프하고 VnTool은 그리기만 한다

**①로 확정됐다.** ②는 같은 규약을 두 번 구현하는 것이고,
규약이 바뀌는 날 양쪽 다 **오류 없이 조용히 어긋난다** — 이 프로젝트가 반복해서 피해 온 실패다.
③은 유니티를 켜야만 프리뷰가 도는 것이라 저작 도구로서 후퇴다.

①이 가능하다고 판단한 근거:
  - 이 저장소의 연출은 전부 UI로 재생된다(카메라도 리그 시뮬).
  - 좌표가 전부 RigSpaceRoot 픽셀 기준이다(runtime-contract.md §104).
  - VnTool도 기준 해상도 캔버스에 그린다 — **두 좌표계는 원래 같은 모양이다.**
  - 셰이더가 필요한 것은 커맨드 201개 중 37개(18%)의 시각 효과 부분뿐이고,
    그나마 그 **상태는 순수 데이터**다(블러 반경, 비네트 강도, 마스크 종류).

그래서 순서가 이렇게 된다:
  이 저장소에서 순수 코어(Ked.Presentation.Core)를 뽑는다
    → VnTool이 그걸 참조한다
    → VnTool이 실제 구도를 그린다 (Phase 2b)

**즉 지금 네가 하는 일이 VnTool Phase 2b의 전제다.**

═══════════════════════════════════════════════════════════
3. 이미 확정된 것 — 다시 논의하지 말 것
═══════════════════════════════════════════════════════════

- 코어는 netstandard2.1, 외부 의존성 0, **UnityEngine 참조 0**.
  (asmdef의 noEngineReferences: true로 이미 강제돼 있다 — 풀지 말 것)
- 리듀서는 **순수 함수**: Apply(state, command, catalog, tuning) -> state.
  시간·랜덤·IO·전역 상태 없음.
- 게임별 값(리그 스키마·프리셋·기준 해상도)은 코드가 아니라 **tuning 인자**로 온다.
  코어에 게임 고유 수치를 박지 말 것.
- 인식 못 한 커맨드는 **버리지 말고 Unhandled 목록에 보존**한다(커맨드명 + 출처).
  조용한 실패를 만들지 않는 것이 이 프로젝트의 규율이다.
- 좌표는 전부 기준 해상도 픽셀. 호스트가 뷰포트로 스케일한다.
- **1u = 가로 기준 해상도 ÷ 48** (절대 40px이 아니다. 2026-08-05 확정)
- CommandBase는 코루틴 호스트(MonoBehaviour)를 물고 있어 **코어로 가지 않는다.**
  코어에 가는 것은 각 커맨드의 "스펙 → 목표 상태" 변환부뿐이다.
- 트윈 실행부와 DOTween 의존(67파일)은 호스트에 남는다.
  정지 프레임에 필요한 것은 ClaimTarget이 산출하는 목표값뿐이다.

4. 이 저장소에 대해 이미 조사된 사실 — 다시 세지 말 것
═══════════════════════════════════════════════════════════

(core-extraction-survey.md, 572파일 / 78,215줄 조사)

- MonoBehaviour 엉킴은 거의 없다 (Commands/ 116파일 중 1개, PresentationCore/ 54파일 중 2개).
  커맨드는 전부 평범한 C# 클래스다.
- **진짜 엉킴은 RectTransform(402회)을 상태 담지체로 쓰는 것이다.**
  별도 상태 모델이 없어서 "현재 상태를 물어볼 곳이 트랜스폼밖에 없다".
  → 그래서 이 작업은 "MonoBehaviour에서 로직 뜯어내기"가 아니라
    **"트랜스폼을 읽고 쓰던 자리를 상태 값으로 바꾸기"**다.
- ClaimTarget 패턴 51개 커맨드가 "목표값 계산"과 "트윈"을 **이미 분리해 두었다.**
  단 이건 규약이 아니라 관습이다 — CommandBase에 선언이 없고 51곳이 각자 구현했다.
  **이 51곳의 표준화가 실제 작업량이다.**
- ShotResponse/CharacterPlacementTargetLedger가 **StageState의 원형으로 이미 돌고 있다.**
  "트윈이 다 끝났다면 어디에 있을 것인가"를 별도 보관 중이다.
  바꿀 것은 둘뿐: 키를 RectTransform → 논리 식별자로, 측정을 "유니티에 잠깐 써넣고
  되돌리기" → 순수 변환 수학으로.
- CaptureCurrent()에 쓸 패턴이 이미 둘 있다:
  PresentationResponseCoordinateMapper.CaptureBaseMeasure,
  CharacterPlacementTargetLedger.WorldPointToSettledParentLocalPoint.

6. 앞으로 할 일
═══════════════════════════════════════════════════════════

U13-b (코어 추출) — 여섯 단계. **"커맨드 51개 옮기기"가 아니라 옮길 바닥부터 놓는 일이다.**
  b-0  토큰 마무리 — 1u를 기준 폭 파생으로            ← 다음에 할 것
  b-1  값 타입 + 트랜스폼 수학 + 유니티 대조 하네스    ← 여기가 바닥
  b-2  리그 노드 트리 (StageState의 뼈대)             (U12-전체 필요)
  b-3  Ledger 승격 — "적용→측정→복원" 트릭 제거
  b-4  ClaimTarget 규약화 (표본 5~10개 보고 선행)
  b-5  커맨드 이관 (placement 14 → depth 7 → shot 5 → staging 12)

U12-전체 (데이터 덤프) — U13-b와 병행 가능하지만 **b-2보다는 앞이어야 한다.**
  코어의 tuning 타입 모양이 곧 이 덤프의 스키마이기 때문이다.
  ⚠ 리그 스키마에 anchorMin/anchorMax/pivot/sizeDelta와 부모 rect 크기가 담겨야 한다.
    RectTransform 위치는 단순 TRS가 아니라서, 이게 없으면 코어가 위치를 재현할 수 없다.

U14 (등가성 하네스) — 마지막이자 관문.
  런타임에도 지금까지 "리듀서"라는 물건이 없었으므로, 코어가 옳은지 판정할 수 있는 것은 이것뿐이다.
  **U14 초록불이 VnTool Phase 2b의 착수 조건이다.**

U12-v1 (초상화 덤프) — 위 순서와 독립. 반나절 규모, 즉시 가치. 아직 미착수.

## 이 브리핑을 쓸 때 의도한 것

- **왜가 먼저다.** "asmdef를 그어라"만 주면 세션이 목적을 모르는 채 국소 최적화를 한다.
  두 저장소가 왜 얽혔는지를 먼저 주면 판단이 필요한 자리에서 옳은 쪽을 고른다.
- **다시 세지 말 것을 명시한다.** 조사에 쓴 시간(572파일)을 새 세션이 반복하지 않게.
- **확정된 것을 "다시 논의하지 말 것"으로 못박는다.** 특히 ①/②/③ 선택은 이미 끝났고,
  세션이 "각자 구현이 더 쉬운데요"로 되돌아오면 비싸다.
- **바닥부터라는 순서를 강조한다.** b-5(커맨드 이관)가 가장 눈에 보이는 일이라
  거기부터 손대기 쉬운데, 바닥 없이 시작하면 커맨드마다 임시 우회로가 생긴다.
