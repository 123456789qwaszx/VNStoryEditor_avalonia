═══════════════════════════════════════════════════════════
1. 최종 목표
═══════════════════════════════════════════════════════════

VnTool(C#/.NET 10/Avalonia)은 Unity와 Visual Studio 없이 비주얼노벨을 저작하는 도구다.
작가가 대사·조건·선택지·연출을 만들면 .yarn과 CSV를 내보내고,
ked-presentation-runtime이 Unity에서 실제 게임 화면으로 재생한다.

우리가 만들려는 다음 기반은 다음과 같다.

1. VnTool 안에서도 실제 Unity와 같은 무대 구도를 정지 프레임으로 확인한다.
2. VnTool이 런타임 계산을 흉내 내지 않는다.
3. 런타임에서 분리한 Ked.Presentation.Core를 양쪽이 공유한다.
4. 검증된 정지 프레임을 기반으로 이후 실시간 재생 프리뷰로 확장한다.

단계의 의미:
- Phase 2a: 연출을 저작하고 저장·출력할 수 있는 도구
- Phase 2b: 실제 Unity와 같은 무대 상태를 계산하는 정지 프레임 렌더러
- Phase 2c: 시간축을 포함한 실시간 재생 프리뷰

현재 런타임 작업 U13–U14는 Phase 2a의 잔여 UI 작업이 아니라 Phase 2b의 기반 공사다.

═══════════════════════════════════════════════════════════
2. 반드시 유지할 설계 결정
═══════════════════════════════════════════════════════════

- Ked.Presentation.Core는 netstandard2.1, 외부 의존성 0, UnityEngine 참조 0이다.
- asmdef의 noEngineReferences: true 경계를 풀지 않는다.
- 리듀서는 순수 함수다:
    Apply(state, command, catalog, tuning) -> state
- 시간·랜덤·IO·전역 상태를 코어 계산에 넣지 않는다.
- 게임별 리그·프리셋·기준 해상도는 코드 상수가 아니라 tuning 입력으로 전달한다.
- 좌표는 기준 해상도 픽셀이다.
- 1u = 가로 기준 해상도 ÷ 48이다. 40px로 고정하지 않는다.
- CommandBase, MonoBehaviour, 코루틴, DOTween 실행부는 Unity 호스트에 남긴다.
- 코어로 옮기는 것은 커맨드 스펙에서 최종 목표 상태를 계산하는 부분이다.
- VnTool이 런타임 규칙을 별도로 재구현하지 않는다.
- 미지원 커맨드는 이름·출처·이유와 함께 Unhandled에 남긴다.
- 이름이 비슷하다는 이유로 추측해서 연결하거나 자동 교정하지 않는다.
- 기존 재생 동작 불변이 기본이다.
- 처리하지 않은 축을 성공 또는 등가라고 보고하지 않는다.

═══════════════════════════════════════════════════════════

상태가 충돌하면 다음 순서로 판단한다.
1. 현재 작업 중인 실제 저장소의 코드와 방금 실행한 테스트
2. 현재 브랜치의 Git 커밋 이력
3. 최신 마스터 플랜과 architecture decision 문서
4. 작업 지시서와 handoff 문서
5. 이 프롬프트의 과거 진행 보고

모든 항목을 다음 네 상태 중 하나로 구분한다.
- 검증 완료
- 구현됐지만 필수 검증 미실행
- 과거 보고만 있고 현재 저장소에서 미확인
- 미구현

코드가 존재한다는 이유만으로 검증 완료 처리하지 않는다. Unity를 실행하지 못했다면

═══════════════════════════════════════════════════════════
5. 코드를 수정하기 전에 할 일
═══════════════════════════════════════════════════════════

1. 실제 ked-presentation-runtime 저장소의 절대 경로를 찾는다.
2. 복제본이 여러 개면 각 경로·remote·브랜치·HEAD를 비교한다.
3. 실제 작업 저장소가 불분명하면 수정하지 말고 후보를 보고한다.
4. 현재 브랜치, HEAD 전체 해시, git status, upstream ahead/behind, remote URL,
   최근 U12/U13/U14 커밋, untracked 파일을 확인한다.
5. 미커밋 변경은 사용자의 작업일 수 있으므로 덮어쓰거나 되돌리지 않는다.
6. 명시적 지시 없이 reset, checkout --, pull, push, 강제 삭제를 하지 않는다.
7. 저장소의 CLAUDE.md, AGENTS.md, README, 테스트 실행 문서를 먼저 읽는다.
8. 접근할 수 있으면 다음 근거 문서를 읽는다.
   - docs/ked-presentation-runtime/phase2-runtime-orders.md
   - docs/ked-presentation-runtime/runtime-work-orders.md
   - docs/ked-presentation-runtime/core-extraction-survey.md
   - docs/work-orders/phase2-design-brief.md
   - docs/handoff/architecture-decisions.md
9. Assets/Ked.Presentation.Core/, exporter, Core/EditMode/UnityParity 테스트,
   equivalence harness와 최신 EquivalenceReports를 확인한다.

수정 전에 짧은 재개 보고서를 작성한다.
- 저장소 경로·브랜치·HEAD·dirty 여부
- 실제 확인한 문서와 테스트
- U12-전체, U13, U14, U12-v1 상태표
- 문서와 코드가 충돌하는 부분
- 기준선 테스트 결과
- 가장 먼저 처리할 작업 하나와 선택 근거
- 예상 변경 파일과 수용 기준

다음 상황에서는 수정 전에 멈추고 질문한다.
- 실제 작업 저장소를 특정할 수 없음
- 사용자 미커밋 변경과 작업 범위가 겹침
- 기존 기준선 테스트가 실패하고 원인이 불분명함
- 문서와 코드 충돌이 설계 선택을 바꿈
- 필요한 Unity 버전·덤프·외부 파일이 없어 구현 방향이 달라짐
- 삭제, 강제 Git 조작, push가 필요함

장애물이 없다면 재개 보고만 하고 멈추지 말고 가장 앞선 실제 미완료 작업 하나를 진행한다.

8. 작업·커밋·보고 규율
═══════════════════════════════════════════════════════════

- 한 작업 단위에 한 원인 클래스만 다룬다.
- 관련 없는 리팩터링이나 기능 추가를 섞지 않는다.
- 먼저 현재 동작과 관련 테스트를 읽고, 수용 기준을 테스트 가능한 문장으로 쓴다.
- 최소 변경 후 관련 테스트 → 전체 회귀 → Unity 검증 순으로 실행한다.
- git diff, git diff --check, 변경 파일 범위를 확인한다.
- 작업 단위 하나만 커밋한다. 명시적 요청 없이 push하지 않는다.
- 실패한 테스트와 실행하지 못한 필수 검증을 숨기지 않는다.
- 처리하지 못한 커맨드는 Unhandled에 보존한다.

완료 보고에 반드시 포함할 것:
- 저장소 절대 경로·브랜치·HEAD
- 커밋 전체 해시와 메시지
- 변경 파일과 핵심 내용
- 실행한 테스트와 결과
- 실행하지 못한 검증과 이유
- 작업 트리와 upstream ahead/behind
- push 여부
- 다음 작업 단위 하나

각 작업 끝에 다음 체크포인트를 남긴다.
- 현재 목표
- 방금 완료한 작업 단위
- 저장소/브랜치/HEAD
- 검증 완료와 미검증 항목
- 남은 불일치와 Unhandled
- 다음 작업 단위
- 다음에 처음 읽을 파일
- 다음에 처음 실행할 테스트

먼저 이 프로젝트의 목표와 작업 방식에 대한 이해를 5줄 이내로 확인한 뒤,
실제 저장소 상태 복원부터 시작해라.
