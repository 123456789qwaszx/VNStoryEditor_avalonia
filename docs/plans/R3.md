# R3. 결정적 출력과 선택지 순서 호환성 — 계획서

> 상위 계획: [PLAN.md](PLAN.md). 상태: **완료 (2026-09-03)**.

## 1. 목표와 한 줄 요약

같은 원본은 같은 바이트를 만들고, 배포 후 선택지 순서가 서버 이력의 뜻을 조용히 바꾸지 못하게 한다.

끝나면: checksum 변화는 실제 콘텐츠 변화의 결과이며, `OptionIndex` 호환 위험은 배포 전에 드러난다.

## 2. 선행 조건

- [x] R2 완료로 JSON 스키마가 안정됨.
- [x] [D-R3] 기준선은 프로젝트 옆 `release-baselines/`의 명시적 출시 스냅샷이다.
- [x] [D-R3b] 편집은 허용하되, 기존 OptionIndex 의미가 이동하면 배포 산출물 갱신을 막는다.
- [x] 서버 `spring-prepare/dev`가 업로드 raw body 바이트를 SHA-256으로 계산함을 확인했다.

### 결정 근거

- `exported/`는 다시 읽을 때 자동으로 덮이므로 출시 기준선이 될 수 없다.
- manifest는 목차의 정본이지 챕터 본문·배포 이력의 소유자가 아니다.
- 서버는 JSON을 정규화하지 않는다. UTF-8 원본 바이트가 다르면 새 checksum·새 버전이다.
- 서버 선택 이력은 `episodeId + optionIndex`를 저장한다. 따라서 기존 선택지 앞 삽입·삭제·교환은
  과거 순번의 뜻을 바꾼다.
- 라벨·조건·효과 수정은 배열 자리를 이동시키지 않는다. 새 서버 버전의 정상 콘텐츠 변경이므로
  R3의 순서 관문으로 막지 않는다.

## 3. 숙련자의 사고흐름

1. **결정성은 의미 비교가 아니다.** SHA-256 계약에서는 공백과 개행도 데이터다.
2. **순서는 UI 장식이 아니다.** `NextOptions[i]`의 i가 서버 선택 이력이다.
3. **모든 변경을 막지는 않는다.** 개발 중 재정렬과 배포 후 호환 변경을 구분할 기준선이 필요하다.
4. **불안정 원천을 센다.** Dictionary/HashSet 열거, 파일 시스템 순서, 문화권, 개행, JSON 옵션, 시간값을 검사한다.

## 5. 결정성 계약

고정해야 할 것:

- UTF-8 인코딩과 BOM 정책
- 개행 문자
- JSON 들여쓰기와 속성 순서
- 숫자·문자열 문화권 비의존
- Stats와 Nodes의 순서 근거
- NextOptions는 반드시 간선 SourceRow
- 조건·스탯 변화 배열의 순서 근거
- 출력에 현재 시각·절대 경로 등 비결정 값 없음

## 6. 선택지 호환성

비교 키 후보:

- ChapterId + FromEpisodeId
- 이전 `NextOptions`의 TargetEpisodeId·ChoiceLabel·ViaNodeId·조건·효과
- 현행 순번

단순 라벨 비교만으로는 부족하다. 같은 라벨의 서로 다른 선택지가 있을 수 있다. 안정 ID가 계약에 없으므로 R3은 기존 배열 의미가 이동했음을 탐지하는 데 집중한다.

## 7. 주의사항

| 증상 | 원인 | 대응 |
|---|---|---|
| 의미 동일인데 checksum 변경 | 순서·개행·인코딩 불안정 | byte golden |
| 테스트 PC에서만 동일 | OS 개행 의존 | 명시 개행 |
| Dictionary 순서가 우연히 안정 | 구현 세부 의존 | 출력 전 명시 정렬 |
| 라벨만 같아 변경을 놓침 | 약한 선택지 동일성 | 목적지·조건·효과 함께 비교 |
| 개발 중 경고 폭주 | 기준선 개념 없음 | 배포본과 작업본 구분 |
