## 0. 변수는 두 층이다 — 이 설계의 심장

소유자 확정:

> 대사 엑셀의 변수는 **플레이어의 고정되고 저장되는 스탯**이다.
> 기존 툴에서 조건을 만들고 선택지를 주고 `set`을 하는 건 **그 안에서만 노는 것**이다.
> 마지막에 그 놀던 데이터를 **고정 스탯으로 환산**해서, 진짜 챕터·에피소드를 넘나들 때 쓴다.

| | **Tier 1 — 로컬 (노는 층)** | **Tier 2 — 고정 스탯 (저장되는 층)** |
|---|---|---|
| 정체 | 에피소드 내부의 임시 변수 | 플레이어 스탯 2~5개, 정수 |
| 저작 | 기존 툴의 대사노드(조건·선택지·set) — 표현력 제한 없음 | 챕터 엑셀 `스탯` 시트 (원천은 `game.definition.json`) |
| 수명 | 에피소드 안에서만 | 세이브에 남고 챕터를 넘나든다 |
| 런타임 거처 | Yarn `InMemoryVariableStorage` | `EpisodeSelectionStateData.Stats` |
| 누가 읽나 | 그 에피소드의 대사 논리 | **챕터 그래프의 해금·선택 가능 판별** |

### 왜 이 구조가 공짜로 안전한가

계약서 **C5**: "세이브에 변수 스냅샷이 없다. 로드는 노드 처음부터 시킹 리플레이하며 `<<set>>`이 재실행되어 변수가 재구축된다."

즉 **Yarn 변수는 런타임 구조상 이미 노드 로컬에 가깝다.** 소유자가 말한 "그 안에서만 노는 거야"가 억지 규칙이 아니라 런타임이 이미 그렇게 동작하는 것이다. 그래서:

- **에피소드 = 트랜잭션 경계.** Tier 2는 에피소드 끝에서 한 번만 바뀐다.
- 에피소드 중간 세이브/로드 → Tier 1은 리플레이로 재구축(C5), Tier 2는 미변경. **안전.**
- 에피소드 내부 롤백 → Tier 1만 영향. **안전.**
- 에피소드 중도 이탈 → Tier 2 미변경. 재플레이 시 처음부터. **중복 가산 없음.**

### ⚠ 그래서 나오는 규칙 하나 — 엑셀의 스탯변화도 즉시 반영하지 않는다

에피소드 엑셀의 `스탯변화` 열(`trust +1`)을 **라인마다 즉시 Tier 2에 쓰면 위 안전성이 전부 깨진다** (중도 이탈 시 절반만 반영 → 재플레이에서 중복 가산).

**그러므로: 엑셀의 스탯변화도 Tier 1에 누적되고, 에피소드 끝에서 한 번 환산된다.** 저작자 눈에는 `trust +1`이지만 실행은 로컬 누적 → 끝에서 일괄 커밋이다. 소유자가 말한 "마지막에 환산"이 엑셀 경로와 툴 경로 **양쪽에 똑같이** 적용된다.

### 환산이 실제로 일어나는 자리 (이미 코드에 있다)

`YarnVariableBridge`의 `ApplyRuntimeStateBeforeDialogue` / `CollectRuntimeStateAfterDialogue` 왕복이 정확히 이 환산이다 — 대화 전에 고정 스탯을 Yarn에 넣고, 대화 후에 Yarn에서 거둬 고정 스탯에 반영.

**⚠ 그런데 이 브리지는 어디서도 생성되지 않는다(사장 코드).** 지금은 대사에서 바꾼 값이 에피소드 해금에 전혀 반영되지 않는다. **G9가 없으면 이 레이어 전체가 장식이다.** G1과 병행 착수할 것.

**Tier 구분 방법**: 예약 접두 같은 마법이 아니라 **명시 목록**으로 한다. 브리지는 `스탯` 시트(=`game.definition.json`)에 선언된 2~5개 키만 왕복하고, 나머지 Yarn 변수는 건드리지 않는다 → 자동으로 Tier 1이 된다. (자동 추측 금지 원칙)

## 0.5 완전한 분리 — 세 가지 보증과 그 장치

소유자가 밝힌 이 설계의 목적:

> 작가가 조건·변수를 **막 추가해도 뭔 짓을 해도 실패할 일이 없어야** 한다.
> 시나리오 작가가 뭘 잘못 건드려서 **특정 에피소드로 절대 못 가는** 일이 없어야 한다.
> 프로그래머가 기능을 추가했는데 **호환이 깨지는** 일이 없어야 한다. **완전한 분리.**

**분리의 실체는 경계면의 크기다.** 두 층이 주고받는 것은 **에피소드 끝 1회, 2~5개 정수**뿐이다. 이게 전부라서 안쪽에서 무슨 일이 벌어져도 밖으로 새지 않는다. 아래 세 보증은 그 경계면에서 파생된다.

또 하나의 축은 **무해석성**이다. 엑셀의 조건 라벨은 `ConditionDefinition{Name=라벨, Expression=식}`으로 그대로 실려 가고, 그 클래스 주석이 못 박은 대로 **VnTool은 Expression의 내용을 해석하지 않는다**. 툴이 식을 이해하지 않으므로 툴에 기능이 추가돼도 식의 의미가 변할 수 없다.

### 보증 1 — 작가가 Tier 1에서 무엇을 해도 게임이 깨지지 않는다

| 장치 | 내용 |
|---|---|
| 세이브에 Tier 1이 없다 | 계약서 C5. Yarn 변수는 저장되지 않고 리플레이로 재구축된다 → **Tier 1을 아무리 바꿔도 세이브 호환이 깨지지 않는다.** 이 보증의 뿌리 |
| 자동 선언 | 작가가 변수를 추가하면 이미터가 `<<declare>>`를 자동 출력한다(계약서 D4 — 런타임에 declare가 없으므로 이미터 몫). 선언 누락으로 컴파일이 깨지는 경로를 없앤다 |
| **⚠ 구멍 A — 이름 충돌** | 작가가 로컬 변수를 `trust`로 지으면 Tier 2 스탯과 충돌해 브리지가 그걸 거둬 간다 → 분리 파괴. **해결: 이미터가 Tier 1에 자동 네임스페이스를 붙여 출력한다**(예: 작가가 보는 `kindness` → 출력 `$__ep_kindness`). 충돌이 **구조적으로 불가능**해지고 작가는 이름을 아무렇게나 지어도 된다 |
| **⚠ 구멍 B — 선택지 순서** | 계약서 C3: 선택 기록이 **위치 기반**이라 작가가 옵션 순서를 바꾸면 기존 세이브가 **다른 선택지를 리플레이**한다. Tier 1 안의 일인데 세이브로 새는 유일한 통로다. **해결: 런타임 U4**(OptionId·lineId 우선 매칭, 서수는 폴백) — 이 보증의 전제다 |

> **네임스페이스는 "예약 접두 마법"과 다르다.** 브리지가 접두를 보고 *무엇을 거둘지 추측*하는 것은 금지다(자동 추측 금지). 반면 이미터가 *자기 출력에 네임스페이스를 붙이는 것*은 구성이지 추측이 아니다. 브리지는 여전히 명시 목록(`스탯` 시트의 2~5개)만 왕복한다 — 두 장치가 서로를 보강한다.

### 보증 2 — 특정 에피소드로 절대 못 가는 상태를 만들 수 없다

에피소드간 연결·해금 조건은 **챕터 데이터의 소관이고 작가가 손대지 않는다**(파이프라인 ①). 그러나 에피소드 엑셀의 `스탯변화`가 Tier 2를 바꾸므로, 작가가 스탯을 충분히 주지 않아 `trust >= 3` 게이트가 영구히 닫히는 일은 **여전히 가능하다.**

**해결: 정적 도달성 증명을 검증기에 넣는다** (G7).

각 에피소드에 대해 "시작 에피소드에서 출발해 이 노드의 조건을 만족시키는 경로가 존재하는가"를 탐색한다. 없으면 오류 + **어느 조건이 불가능한지 지목**한다.

> **이것이 G-3(정수 고정)의 두 번째 배당금이다.** 스탯이 2~5개 · 정수 · `최소~최대` 유한 범위이므로 상태공간이 작고 **완전 탐색이 가능하다.** float이면 상태공간이 무한해 도달성이 결정 불가능해진다. 경계값 버그를 막으려고 정수로 고정한 결정이, 이 보증을 **가능하게** 만들었다.

작가가 저장하는 순간 검증기가 돌므로, 도달 불가는 **플레이어가 발견하는 것이 아니라 저작 시점에 잡힌다.** 픽스처(G6)는 "이 조건에서 어디로 가나"를 보는 도구이고, 도달성 증명은 "어떤 조건에서든 갈 수 있나"를 보는 도구다 — 둘은 다르고 둘 다 필요하다.

### 보증 3 — 프로그래머가 기능을 추가해도 호환이 깨지지 않는다

| 장치 | 내용 |
|---|---|
| 경계면 동결 | 두 층이 주고받는 것은 2~5개 정수뿐이다. **경계면을 넓히는 변경은 반려**(§6) |
| 무해석성 | 툴이 조건식을 해석하지 않으므로 툴 기능 추가가 식의 의미를 바꿀 수 없다 |
| 추가만 하위호환 | 스탯 추가 = 구 세이브에 누락 → 초기값 폴백(허용). 스탯 **제거·의미 변경**은 스키마 버전 상승 + 마이그레이션 필수. `EpisodeCondition`의 새 `Kind` 추가는 가산적이라 안전 |
| **⚠ 구멍 C — U15가 이 보증을 깬다** | `runtime-work-orders.md` U15의 세이브 v2가 "**변수 스냅샷(전 `$`변수)**"를 담는다. Tier 1이 세이브에 들어가면 보증 1의 뿌리(C5)가 사라지고, 로컬 변수 이름·의미를 바꿀 때마다 구 세이브와 어긋난다 |

> **구멍 C의 해결: U15의 변수 스냅샷은 Tier 2만 담는다.**
> 근거 — U15의 로드는 "**VM 무음 스프린트**(라인 순회하되 커맨드 배치만 폐기)"다. VM이 도는 동안 `<<set>>`은 그대로 실행되므로 **Tier 1은 스프린트가 이미 재구축한다.** 스냅샷에 담을 필요가 없다. 즉 이 제한은 보증을 살리면서 U15를 **더 단순하게** 만든다.
> 이로써 `runtime-work-orders.md`의 소유자 결정 #5("세이브 v2에서 변수 '전체' 스냅샷 범위")가 닫힌다 → **Tier 2만.**

### 요약 — 누가 무엇을 깰 수 없는가

| 주체 | 자유롭게 할 수 있는 것 | 구조적으로 깰 수 없는 것 | 그 이유 |
|---|---|---|---|
| 시나리오 작가 | 조건·변수·선택지 무제한 추가 (Tier 1) | 세이브 호환 | C5 + 자동 네임스페이스 + U4 |
| 시나리오 작가 | 대사·스탯변화 (엑셀) | 에피소드 도달 불가 상태 | G7 도달성 증명 |
| 기획자 | 챕터 구조·조건·잠금 | 대사 내용을 몰라도 됨 | 경계면이 2~5개 정수뿐 |
| 프로그래머 | 툴·런타임 기능 추가 | 기존 콘텐츠 호환 | 경계면 동결 + 무해석성 + 가산적 스키마 |

## 1. 파이프라인 — 5단계

```
① 챕터 데이터 (엑셀)           작가가 신경쓰지 않는 층
   에피소드 목록 · 에피소드간 연결 · 위치 · 조건 라벨↔식 · 스탯 선언
        │
        ▼
② 챕터·에피소드 그래프 뷰       데이터대로 자동 생성 · 편집은 해당 셀 쓰기(G-2 v2)
   챕터 선택 → 내부 노드·간선 렌더 · 잠금 시각화 · 픽스처로 재생루트 하이라이트
        │  (에피소드 노드 클릭)
        ▼
③ 에피소드 엑셀 (대본)          작가의 층
   그냥 대본을 쓴다 · 조건은 라벨로 걸고 IN/OUT 인덱스 지정 · 마지막 라인만 특별취급
        │  (저장)
        ▼
④ 평평화 파서                   조건 구간을 조건 바로 아래로 옮겨 펴고 Yarn 문법 텍스트로
        │
        ▼
⑤ 기존 툴의 대사노드            텍스트를 자기 형태로 변환 · 연출·세밀한 논리는 여기서
```

### ④→⑤에 새 임포터가 필요 없다 — 이미 만들어 뒀다

| 필요한 것 | 이미 있는 것 |
|---|---|
| `<<if>>` `<<elseif>>` `<<endif>>` 문법 표기·해석 | **X11** (ScenarioOnly를 실제 Yarn 문법으로 전환) |
| `화자: 대사` 텍스트 → 라인 + **diff 기반 LineId 보존** | **X12(a)** 붙여넣기 파서 |
| 그 파서가 지워지지 않고 남아 있음 | **XL6** — "ScenarioOnly 편집은 비활성화하되 파서·diff 코드는 삭제하지 않는다" |
| 조건 라벨 ↔ 식의 분리 | `ConditionDefinition{Name, Expression}` — 주석에 "**Expression은 게임이 평가할 식이며 VnTool은 내용을 해석하지 않는다**" |
| 조건 갈래의 출구 앵커 | `DialogueNode.BranchExits` — "**갈래를 여는 줄의 Id로 기억한다**" |

즉 ⑤는 신규 개발이 아니라 **기존 파서에 평평화된 텍스트를 먹이는 일**이다. `.yarn` 전체 역파싱(마스터 플랜 §3 비범위)이 아니라 X11이 정의한 제한된 부분집합만 다룬다.

**엑셀 조건 행 → 툴 모델 매핑** (두 설계가 만나는 이음매):
엑셀의 조건 행은 LineId가 없다 → 평평화 시 `<<if 식>>`이 되고 → 파서가 **그 아래 첫 대사 줄**에 조건을 부착한다 → 그 줄이 `BranchExits`가 말하는 "갈래를 여는 줄"이 된다. 양쪽 모델이 어긋나지 않는다.

### 3.3 구간 = INPUT/OUT 태그로 감싼 줄 묶음

구간은 **인덱스 범위가 아니라 태그로 경계가 정해진다.**

```
31  OPTION   IN=900     "옵션1 라벨"
32  OPTION              "옵션2 라벨"
34  (대사)               ← 수렴 지점
…
900 (대사)   태그=INPUT              ← 구간 진입
…
908 (대사)   태그=OUT   OUT=34       ← 구간 종료 + 나갈 곳

실행:  31 → 900 … 908 → 34
```

**강제 규칙 (검증기가 막는다)**

| # | 규칙 |
|---|---|
| 1 | `IN=X`가 있으면 인덱스 `X` 행에 `INPUT` 태그가 있어야 한다 |
| 2 | `INPUT`이 있으면 그 아래에 짝이 되는 `OUT` 태그가 **반드시** 있어야 한다 (소유자 표현: "붙도록 강제") |
| 3 | 구간 = `INPUT` 행부터 `OUT` 행까지 **양끝 포함** |
| 4 | 한 `INPUT`을 둘 이상이 가리키면 오류 (G-6 구간 재사용 금지) |
| 5 | 구간 안에 또 `IN`이 있는 **중첩 금지.** 엑셀의 인덱스·태그 모델로는 중첩 구간의 경계가 모호해지기 때문이다 — **하위 툴의 지원 여부와 무관한 이 규격 자체의 제약이다** (아래 ⚠) |
| 6 | `OUT` 대상은 **평평화 후의 자연 수렴 지점**이어야 한다 (아래 ⚠) |

> ⚠ **규칙 5의 근거가 바뀌었다 (2026-08-12).** 예전 근거는 "마스터 플랜 §3의 중첩 조건 비범위"였는데 **W54·W55로 낡았다** — 기존 툴은 이제 조건 안 선택지를 지원하고(깊이 0~2), `EndIf` 한 줄이 열린 선택지도 함께 닫는다.
>
> **제약 자체는 유지한다.** 근거가 하위 툴의 한계가 아니라 **이 규격 자체의 것**이기 때문이다: 구간의 경계는 `INPUT`/`OUT` 태그 <b>한 쌍</b>으로 정해지는데, 구간 안에서 또 `IN`이 열리면 안쪽 `OUT`이 어느 쌍을 닫는지가 표만 보고는 결정되지 않는다. 들여쓰기 같은 시각적 중첩 표현이 없는 평평한 표에서 이건 사람에게도 툴에게도 모호하다.
>
> **툴이 엑셀보다 넓게 받는 것은 안전하다.** 엑셀 규격이 툴이 표현할 수 있는 것의 부분집합으로 남을 뿐이고, 부분집합은 언제든 넓힐 수 있다. 반대(엑셀이 툴보다 넓음)만이 위험하다.

### 3.4 평평화 규칙 (④)

`IN`을 가진 행 자리에 그 구간을 **옮겨 넣는다.** 옮긴 행들은 원래 위치에서 사라진다 — 규칙 4가 복제를 막으므로 **LineId 전역 유일성(계약서 C1)이 지켜진다.**

```
IF 행    →   <<if {라벨의 조건식}>>
                INPUT행 … OUT행   (여기로 이동)
             <<endif>>
             OUT 대상 인덱스부터 계속

OPTION 행 →  -> {라벨}
                INPUT행 … OUT행   (옵션 본문으로 이동)
             (블록 종료 후) OUT 대상 인덱스부터 계속
```

> ⚠ **`OUT`이 실질적으로 하는 일 — 이걸 알고 쓰셔야 합니다.**
> Yarn에는 **노드 안의 줄 단위 goto가 없습니다.** 그래서 `OUT=34`는 "34로 점프하라"는 명령으로 번역될 수 없고, **"평평화하면 자연히 34로 흐른다"는 선언**이 됩니다. 검증기가 실제로 그렇게 흐르는지 대조해서, 어긋나면 오류를 냅니다.
> 이게 나쁜 게 아니라 오히려 좋습니다 — 기획자는 흐름을 눈에 보이게 적고, 툴은 그게 사실인지 보증합니다. "하드코딩 같지만 직관적"이 여기서 **검수 장치**가 됩니다.

**선택지에서 옵션마다 `OUT`이 갈릴 때** (option1 `OUT=34`, option2 `OUT=50`): 자연 낙하로는 둘을 동시에 만족시킬 수 없다.
- 모든 옵션의 `OUT`이 `END`면 → 에피소드 종료. 문제 없음 (선택지가 맨 끝이라 정상 경로).
- 모두 같은 인덱스로 수렴하면 → 문제 없음.
- 서로 다른 비-`END` 인덱스로 갈리면 → **v1 오류.** 승격 경로는 기존 툴이 이미 쓰는 `$__ch_N` 선택 전환 체인(마스터 플랜 §2.3)이며, 필요해지면 그걸 재사용한다(G2 계획서에서 결정).

#### ⚠ G3-1. LineId를 텍스트 경계에서 잃지 않는다

`ApplyScenarioText`(`src/Vn.Authoring/Editing/ProjectEditor.Scripts.cs:66`)는 파싱 결과를 `ScriptSynchronizer.Plan`에 넘기고, `Ambiguous`가 **하나라도** 있으면 아무것도 바꾸지 않는다. 사람이 텍스트를 손으로 붙여넣는 경우엔 이게 옳은 보수성이다 — 도구가 남의 줄에 남의 ID를 함부로 물릴 바에 멈추는 게 낫다.

**그러나 엑셀 경로는 사정이 다르다. 시트의 `LineId` 열(§3.2 B열)로 각 줄의 신원을 이미 알고 있다.** 이 지식을 텍스트로 넘어가면서 버리면, 확실한 **ID 매칭이 내용 추정으로 격하**된다. 결과는 두 가지로 나쁘다 — 비슷한 대사가 여러 줄이면 동기화기가 확신하지 못해 `Ambiguous`를 내고, 그러면 **기획자의 멀쩡한 저장이 통째로 거부된다.**

**그러므로:**

1. **평평화 산출 텍스트가 LineId를 실어 보낸다.** 계약서 C1의 `#line:` 태그가 그 그릇이다 — 새 표기를 발명하지 말 것.
2. **`ScenarioTextParser`가 그 태그를 읽어** 라인의 신원으로 떼어내고, `ScriptSynchronizer`에 ID를 넘긴다. 동기화는 **내용 추정이 아니라 ID 일치로** 매칭한다.
3. **ID가 있는 라인에서는 `Ambiguous`가 구조적으로 발생하지 않아야 한다.** 그래도 발생하면 통째 거부하되 **어느 행 때문인지 목록으로 보고**한다(규칙 14). 조용한 무반영이 최악이다 — 기획자는 저장했다고 믿는데 아무것도 안 바뀐 상태가 된다.

**표기 정본 = Yarn 접미형 `#line:ln_0001`** (확정, 2026-08-12). 근거 셋:

1. **계약서 C1이 요구하는 형식이고, 실제 산출물이 이미 그 형식이다** — `YarnBundleEmitter`·`YarnPreviewFormatter`가 story 대사 라인에 ` #line:{id}`를 단다. 정본을 여기 맞추면 새 표기가 하나도 늘지 않는다.
2. **Scenario 전용 접두 `[ln_0001]`을 정본으로 삼으면 이미터와 다른 표기가 하나 더 생긴다** — 두 표기를 오가는 변환이 어딘가에 살고, 그 자리가 규약 사본이 된다.
3. **X12 손 붙여넣기 경로도 함께 이득이다** — 파서가 태그를 분리해 `ScriptSynchronizer`에 ID로 넘기면, 사람이 `#line:` 붙은 텍스트(내보낸 `.yarn`에서 복사한 것)를 붙여넣어도 신원이 유지된다. 지금은 그 태그가 대사 본문에 섞여 들어간다.

**남은 계획 항목**: `ScenarioOnly` 프리셋의 `includeLineId`를 켤지, 아니면 **엑셀 경로 전용 출력 프리셋**을 따로 둘지. 켜면 사람이 읽는 화면에 ID가 늘 보이고, 따로 두면 프리셋이 하나 늘어난다. G2 계획서에서 결정한다.

> **세션 0 선조사 (2026-08-12) — 지금은 둘 다 깨진다. 계획서는 여기서 출발하면 된다.**

> | 사실 | 근거 |

**수용**: 새 임포터 코드를 만들지 않았음을 코드 경로로 증명. 견본 에피소드가 대사노드에 들어가고 조건 갈래가 그래프에 보인다. **엑셀 왕복에서 LineId가 ID 일치로 보존되고, `Ambiguous`로 인한 통째 거부가 발생하지 않는다** — 발생 시 원인 행이 목록으로 보고된다. **행 삭제로 함께 접힌 조건·`set`·갈래 출구가 행별 목록과 배지로 보고된다**(G3-2).

## 7. 소유자 결정 대기

1. ~~`OUT`의 의미~~ — **확정(2026-08)**: `OUT`은 구간 마지막 줄에 붙는 **태그**이며 값은 **나갈 목적지 인덱스**다. `INPUT`과 짝이 강제된다. §3.3·§3.4에 반영 완료.
2. **인덱스 간격 소진 시** — 10·20·30 사이가 다 차면(11~19까지 씀) 어떻게 할지. 권고: 툴이 자동 재번호하지 않고 **"간격 부족" 경고만** 내고 사람이 재번호한다. 자동 보정은 IN/OUT 참조를 조용히 바꾸는 일이라 위험하다.
3. **Tier 1 네임스페이스 표기** — 구멍 A의 해결로 이미터가 자동 네임스페이스를 붙이기로 했다(§0.5). 실제 접두 문자열(`$__ep_` 등)과, 그것이 계약서 §D의 선언 규약·기존 `$__ch_N`과 충돌하지 않는지 G2 계획서에서 확정.
4. ~~**Tier 1 → Tier 2 환산 규칙의 저작 위치**~~ — **닫힘 (2026-08-14)**: 환산 자체가 없다. 대사(엑셀·툴 양쪽)는 Tier 2를 못 만지고, Tier 2는 챕터 간선의 `스탯변화`로만 변한다. 브리지(G9-a)는 Tier 2→Yarn **단방향 주입**(대사 안 조건 판정용)만 남는다 — Collect(거둬 오기)는 필요 없어졌다.
5. **스탯의 범위** — 게임 전역 2~5개로 가정(`game.definition.json` 원천). 챕터별로 다르면 규격이 달라진다. **`최소`·`최대`는 필수다** — 도달성 증명(G7)의 탐색 경계이기 때문이다.
6. **`Attachment` 5종·`EndingRules`** — 런타임이 이미 가진 기능. v1에서 열 노출까지만 할지, 저작까지 할지.
7. **도달 불가를 오류로 막을지, 경고로 둘지** — 의도적으로 도달 불가인 노드(폐기 예정·미완성)가 있을 수 있다. 권고: 기본은 오류, `에피소드` 시트에 "도달불가 허용" 열로 명시 예외를 두되 그 사실이 그래프에 표시되게 한다(조용히 넘기지 않음).
