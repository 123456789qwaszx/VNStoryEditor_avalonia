# 저작의 주인을 툴로 옮긴다 — 워크북은 산출물이 된다

기준일: 2026-09-15 · 결정자: 소유자 · 대상: `VNStoryEditor_avalonia`

> **한 문장.** 엑셀에 쓴 것이 툴에 반영되는 것이 아니라, **툴에 쓴 것이 엑셀을 채운다.**

이 문서는 규격 원본이다. 세부 구현은 R-A~R-F 순서를 따르고, 완료 표시는 코드 존재가
아니라 테스트 통과로 붙인다.

---

## 1. 무엇이 바뀌는가

### 1.1 소유권 표 (개정)

| 값 | 기존 주인 | **새 주인** |
|---|---|---|
| 에피소드 구조·간선·선택지·조건·스탯 | `chapters/{Id}.xlsx` | **툴 프로젝트** |
| 대사 본문·화자·라인 구조 | `episodes/{챕터}/{Id}.xlsx` | **툴 프로젝트** (`ScriptDocument`) |
| 연출 노드·커맨드 | 툴 프로젝트 | 그대로 |
| 화자 등록·초상화 매핑 | `game.definition.json` | 그대로 |
| `chapters/*.xlsx` · `episodes/**/*.xlsx` | **원본** | **산출물** |
| `exported/*.progression.json` · Yarn 번들 | 산출물 | 그대로 |

**엑셀이 `exported/`와 같은 편에 선다.** 툴이 쓰고, 사람은 읽는다.

⚠ **"각 값의 주인은 한 곳뿐"은 폐기되지 않는다.** 주인이 옮겨갈 뿐이고, 규칙은 오히려
강해진다 — 양방향이 사라지므로 두 곳이 어긋날 자리 자체가 없어진다.

### 1.2 왜 뒤집는가

소유자 판단(2026-09-15): *"엑셀을 열게 한다는 게 시나리오 작가들의 손발을 묶어 버린다."*

엑셀이 원본이라는 전제는 *"기획자와 작가가 익숙한 도구를 그대로 쓴다"*(README)에서 나왔다.
실제로 협업해 본 결과 그 전제가 성립하지 않았다 — 엑셀의 행·열 규격이 글쓰기를 막는다.

### 1.3 치르기로 한 비용

되돌릴 수 없으므로 명시해 둔다.

- **구글 시트 동시 편집이 불가능해진다.** 툴이 쓰는 파일을 여럿이 동시에 만질 수 없다.
- **작가가 툴을 깔아야 한다.** `publish-windows.ps1`의 휴대용 패키지가 배포 경로의 정본이 된다.
- **충돌 지점이 프로젝트 파일 하나로 모인다.** 지금은 챕터별 엑셀이 갈려 자연히 분업됐다.

## 2. 사라지는 것 — 엑셀이 주인이라서만 존재하던 기계

읽기가 사라지면 아래는 **지킬 이유가 없어진다.** 지우지 않고 두면 다음 사람이 "이건 왜
있지"를 묻는다.

| 대상 | 존재 이유 | 처분 |
|---|---|---|
| `EpisodeSyncService` (역방향) | 워크북 → 노드 | **삭제** |
| `WorkbookParseCache` | 안 바뀐 대본을 다시 파싱하지 않으려고 | **삭제** |
| `WorkbookMigrationGate` | 이행 프로브를 내용 해시로 기억하려고 | **삭제** |
| `WorkbookFolderFingerprint` | 폴더 변경 감지 | **삭제** |
| `ChapterFolderWatcher` (대본 부분) | 엑셀 저장을 0.25초 안에 따라가려고 | **삭제** |
| `DialogueNode.ExcelLineMap` | 엑셀 인덱스 ↔ LineId 매핑 | **삭제** (툴이 LineId의 주인) |
| `EpisodeLineEditor` | 노드의 한 줄을 엑셀 셀로 되쓰기 | **삭제** (전체를 다시 쓴다) |
| `ScriptSynchronizer`의 재동기화 | 다시 읽었을 때 LineId를 잇기 | **임포트 전용으로 강등** |
| 엑셀 잠금 배너 (편집 차단) | 읽기·쓰기 경합 | **의미 변경** — §5.3 |
| `EpisodeLibrary.PushVocabulary` | 엑셀 드롭다운에 어휘 공급 | **삭제** (읽기 전용 산출물엔 드롭다운이 없다) |

> **⚠ 2026-08-24 성능 작업이 통째로 무의미해진다.** 실측 *"워크북 작업의 절반이 '고칠 것
> 없음'만 답하는 프로브였다"*는 다시 읽기를 전제로 한 최적화였다. 다시 읽지 않으면 캐시할
> 것이 없다. **그 작업을 되살리려 하지 말 것** — `ChapterGraphWorkAmountTests`가 지키던
> "일의 횟수" 고정도 함께 의미가 바뀐다.

## 3. 대본 워크북에서 조건 블록을 걷는다

### 3.1 근거 — 이미 죽은 기능이다

`IF` · `ELSEIF` · `ENDIF` 행과 B열 `조건라벨`을 **행째 삭제한다.**

1. 런타임이 **[2] 진행 스탯을 대사 조건에 쓰는 것을 금지**했다
   (`ked-presentation-runtime/docs/scene-boundary-plan.md` §4 G0 — *"대사에서 스탯 표현·분기
   금지. 진행 그래프가 볼 수 없는 숨은 [2] 분기가 대사 속에 있는 것 자체가 도달성 증명의
   사각이었다"*). `<<if>>` 자체는 [3] 전용으로 남았다.
2. 에디터는 R4에서 **내보내기 관문에만** 반영했다 — `YarnBundleEmitter.ValidateProgressionStatReferences`가
   blocking 진단을 낸다.
3. 그런데 대본 워크북의 `조건라벨`은 **챕터 `조건` 시트에서만** 온다(`EpisodeFlattener`).
   그 시트는 전부 [2] 진행 스탯이다.
4. **따라서 대본 엑셀에서 만들 수 있는 조건 블록은 전부 내보내기에서 막힌다.**

검증: `"IF"`를 쓰는 테스트가 10개 파일에 있으나 **이미터까지 가는 것은 하나뿐**이고
(`엑셀_출처_노드의_진행_스탯_Yarn_참조를_발행_전에_막는다`), 그 하나가 **차단을 단언한다.**
대본 IF 블록이 성공적으로 내보내지는 사례는 테스트에 **0건**이다.

### 3.2 조건은 사라지지 않는다 — 자리를 옮길 뿐

`SetNode.Conditions`가 *"조건이 태어나는 유일한 자리"*로 이미 존재한다. 대사 안의 [3] 조건은
연출 그래프에서 저작한다. 걷어내는 것은 **죽은 [2] 경로 하나**다.

### 3.3 기존 워크북의 IF 블록 — 옮기지 않고 보고한다

⛔ **임포터가 기존 IF 블록을 `SetNode` 조건으로 옮기지 않는다.** 그 식의 변수는 [2]이고,
옮기면 금지된 것을 툴 안에 다시 세우는 셈이다.

대신 **진단으로 보고하고 버린다**: *"이 조건 블록은 더 이상 지원되지 않습니다(진행 스탯은
대사에서 읽을 수 없습니다). 분기가 필요하면 챕터 간선의 표시조건·해금조건으로 옮기세요."*
어차피 내보내기에서 막히던 것이므로 **동작하던 기능을 잃지 않는다.**

### 3.4 걷어낼 자리

| 파일 | 무엇 |
|---|---|
| `Chapters/EpisodeWorkbookModel.cs` | `EpisodeRowKind`, 블록 행 모델 |
| `Chapters/EpisodeWorkbookReader.cs` | 블록 판정·짝 검증·블록 행 빗장 |
| `Chapters/EpisodeFlattener.cs` | 조건 → Yarn 번역 경로 |
| `App/Views/ChapterGraphView.axaml.cs` | 조건 어휘 공급 |
| `Chapters/ChapterDiagnostic.cs` | `ConditionLabelUndefined` · `BlockRowIndexStray` |
| `Chapters/EpisodeWorkbookWriter.cs` | `ClearBlockRowIndexes` |
| `Chapters/EpisodeSyncService.cs` | `TidyBlockRows` |

⚠ **진단 코드의 enum 값은 남긴다** — 이 레포의 규율이다(*"값을 지우면 옛 보고·기록의 코드
이름이 다른 뜻으로 밀린다"*). 주석에 폐지 사유와 날짜를 적는다.

⚠ **챕터 워크북의 `조건` 시트는 남는다.** 그것은 간선의 표시조건·해금조건이고, [2]의 정당한
자리다. 이 지시서는 **대본 워크북의 블록 행**만 걷는다.

## 4. 워크북 쓰기는 이미터가 된다

### 4.1 성격 변경

`ChapterWorkbookWriter` · `EpisodeWorkbookWriter`는 "셀 하나 고치기"에서 **"문서 전체를 낸다"**로
바뀐다. 성격이 `YarnBundleEmitter`와 같아지므로 이름도 그렇게 간다:

```
ChapterWorkbookWriter  →  ChapterWorkbookEmitter
EpisodeWorkbookWriter  →  EpisodeWorkbookEmitter
```

### 4.2 사라지는 난제

앞선 설계 상담에서 0-b로 잡았던 **행 삽입·삭제**가 **필요 없어진다.** 전체를 새로 쓰면 삽입도
삭제도 개념이 없다. 인덱스 충돌·신원 보존 문제도 함께 사라진다 — 인덱스는 이제 툴이 정한
순번을 그대로 적는 **출력 열**이다.

### 4.3 지켜야 할 것

- **원자적 쓰기.** 임시 파일을 완성한 뒤 교체한다. 중간 실패로 반쯤 바뀐 워크북을 남기지
  않는다. (런타임의 세이브 규율과 같다 — `PLAN_offline-local-save.md`: *"모든 쓰기는 임시
  파일을 완성한 뒤 교체한다"*)
- **`.bak` 정책 유지.** 덮어쓰기 전 원본을 남긴다.
- **겉모습은 이행이 입힌다** 규율 유지 — `ApplyChapterChrome`을 이미터가 그대로 부른다.
- ⛔ **결정적 바이트는 요구하지 않는다.** SHA-256 계약은 `progression.json`만이다. xlsx는
  zip이라 타임스탬프가 섞이고, 여기에 그 규율을 끌어오면 비용만 는다.

### 4.4 읽기 전용임을 파일이 말해야 한다

사람이 열어서 고칠 수 있는 파일이 "고쳐도 소용없는 파일"이면, **그 사실이 파일 안에 있어야
한다.** 셋을 함께 낸다:

1. **시트 보호**를 건다 (ClosedXML이 지원한다). 암호 없이 — 막는 것이 아니라 알리는 것이다.
2. 각 시트 1행에 머리글보다 위로 한 줄: **`⚠ 이 파일은 VnTool이 만든 산출물입니다. 여기서
   고친 것은 반영되지 않고 다음 저장에 덮어쓰입니다.`**
3. 파일 속성 `Comments`에 같은 문구와 생성 시각.

## 5. 남는 읽기 경로 — 임포트 한 번

### 5.1 임포터로 강등

`ChapterWorkbookReader` · `EpisodeWorkbookReader` · 두 `Migrator`는 **삭제하지 않고 임포터로
격리한다.** 기존 프로젝트를 한 번 들여오는 일회성 관문이다.

```
Chapters/Import/ChapterWorkbookImporter.cs
Chapters/Import/EpisodeWorkbookImporter.cs
```

### 5.2 불변식

- 임포트는 **명시적 동작**이다. 파일 감시가 부르지 않는다.
- 임포트 뒤 그 프로젝트는 **다시 읽지 않는다.** 테스트로 고정한다 — 임포트 후 워크북을
  바깥에서 고쳐도 프로젝트가 변하지 않아야 한다.
- 임포트가 **부분 성공하지 않는다.** 하나라도 해석 못 하면 아무것도 들여오지 않고 진단을 낸다
  (`ScriptSynchronizer`의 *"애매하면 멈춘다"*를 여기로 옮긴다 — 그 규율의 마지막 거처다).

### 5.3 엑셀 잠금의 의미가 바뀐다

지금은 *"엑셀이 파일을 잡고 있으면 툴 편집이 잠긴다"*(붉은 배너)다. **이제 편집을 막을 이유가
없다** — 툴이 원본이므로.

바뀐 뜻: **그 파일을 지금 갱신하지 못했다.** 편집은 계속되고, 저장은 프로젝트에 되며,
워크북 출력만 미뤄진다. 배너 문구도 그렇게 간다 — *"엑셀이 `ch01.xlsx`를 열고 있어 갱신을
미뤘습니다. 닫으면 자동으로 다시 냅니다."*

⚠ **미룬 것을 잊지 않는다.** 실패한 출력 대상을 목록으로 들고, 잠금이 풀리면 다시 낸다.

## 6. [대본] 탭 — 작가의 자리

### 6.1 왜 셋째 탭인가

이 도구의 탭은 곧 역할이다(챕터 그래프 = 기획자, 연출 그래프 = 연출자). **작가만 제 탭이
없었다.** 연출 그래프 우측에 넣으면 작가가 노드·포트·배선이 가득한 판을 열어야 한다.

### 6.2 규격

- 챕터 → 에피소드를 고르고 그 대본만 보인다. **노드도 포트도 없다.**
- 대사는 자유 편집 — 추가·삭제·수정·순서 변경.
- **작가가 텍스트를 쓰면 노드가 생긴다.** 에피소드에 대사 노드가 없으면 저장 시 만든다.
- 화자는 드롭다운(등록부에서). 미등록 이름은 오류가 아니라 표시 대상이다.
- 조건은 **보이지 않는다** — §3에서 대본 층의 조건이 사라졌으므로 보여 줄 것이 없다.
- 저장 = 프로젝트에 저장 + 워크북 재출력. 출력 실패는 §5.3.

### 6.3 줄의 신원은 편집기가 든다

`ScenarioOnly` 텍스트는 `includeLineId: false`다. 화면에 `#line:` 태그를 보이면 지저분하고
작가가 지운다.

→ **편집기가 "보이는 줄 ↔ LineId" 대응표를 들고 편집 조작을 추적한다.** 화면은 순수 텍스트,
내부는 신원이 붙은 줄 목록이다. 통째 붙여넣기처럼 대응이 끊기는 경우에만 내용 매칭으로
떨어지고, 그때는 확인을 요구하고 멈춘다.

### 6.4 재료는 이미 있다

- `ScenarioTextParser` — 자유 텍스트 → 화자·대사 파싱 (322줄, 동작함)
- `ProjectEditor.ApplyScenarioText` — 파싱 → diff → LineId 보존 → 반영 (동작함)
- 막고 있던 것은 두 줄이다: `AddLineButton.IsEnabled = !_excelOwned` ·
  `ApplyScenarioButton.IsEnabled = !_excelOwned`. **뒤집기 뒤에는 `_excelOwned` 개념 자체가
  사라진다** — 모든 노드가 툴 소유다.

## 7. 순서

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| **R-A** | 임포트 경계 세우기 — 리더·이행기를 `Import/`로 격리, 감시자에서 분리 | 임포트 후 워크북을 바깥에서 고쳐도 프로젝트가 안 변한다 (테스트) |
| **R-B** | 워크북 이미터 — 프로젝트 → xlsx 전체 출력, 원자적 쓰기, 읽기 전용 표기 | 같은 프로젝트를 두 번 내면 내용이 같다 · 시트 보호와 경고 문구가 선다 |
| **R-C** | 대본 조건 블록 제거 (규격 v15) | 임포터가 IF 블록을 진단으로 보고하고 버린다 · 이미터가 안 낸다 |
| **R-D** | 역방향 기계 철거 (§2 표) | 삭제 후 전체 테스트 통과 |
| **R-E** | [대본] 탭 | 작가가 텍스트만으로 에피소드 하나를 완성하고 워크북이 나온다 |
| **R-F** | 챕터 편집 경로 전환 — "엑셀 셀에 즉시 저장" → "프로젝트 저장 + 재출력" | 챕터 그래프 편집이 워크북을 직접 쓰지 않는다 |

**R-A와 R-B가 먼저인 이유**: 뒤집기의 위험은 전부 "읽던 것을 안 읽게 되는 순간"에 있다.
쓰기가 먼저 서야 임포트한 데이터를 잃지 않고, 경계가 먼저 서야 무엇이 철거 대상인지 보인다.
R-D를 먼저 하면 되돌릴 길이 없다.

---

## 8. 하지 않는 것

- 챕터 워크북의 `조건` 시트 제거 — [2]의 정당한 자리다
- `progression.json`·Yarn 번들 계약 변경 — 이 작업은 저작 층만 건드린다
- 런타임·서버 저장소 수정
- xlsx 결정적 바이트 출력 (§4.3)
- 기존 IF 블록의 자동 이전 (§3.3)

---

## 9. 되돌리는 법

R-D 전까지는 임포터가 곧 되돌리는 길이다 — 워크북이 여전히 원본을 표현할 수 있으므로,
프로젝트를 버리고 워크북에서 다시 들여오면 된다. **R-D를 지나면 그 길이 닫힌다.**
R-D는 R-A~R-C가 테스트로 굳은 뒤에 착수한다.
