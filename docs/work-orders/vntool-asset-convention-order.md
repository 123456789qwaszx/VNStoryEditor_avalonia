# 작업 지시 — 에셋 연결 권위를 매니페스트에서 규약으로 (W-asset-02)

## 0. 이 지시의 성격

**설계 방향 교정이다. 재작성이 아니다.**

현재 `Vn.Authoring/Assets/*`의 구현 품질은 문제가 없다.
`PreviewAssetLibrary`가 문제를 침묵시키지 않는 것, `PortraitManifest`가 형식 버전을 거부하는 것,
`AssetExplorerModel`이 계산과 표시를 가르는 것 — 전부 유지한다.

바꿀 것은 **연결을 무엇이 결정하는가** 하나다.

### 왜 어긋났는지 (배경 설명, 자책 불필요)

`runtime-ui-tooling-principles.md` §3.5의 표가
"초상화 = 키 매핑형 = 매핑 덤프 필요"로 읽히게 쓰여 있었다.
그 표는 **런타임의 저장 방식**을 서술한 것인데, 툴의 저장 방식까지 정하는 것처럼 읽혔다.
지시가 부정확했던 것이지 판단이 틀린 게 아니다.

---

## 1. 교정 원리

> **런타임과 툴이 공유하는 것은 키 공간이지 저장 방식이 아니다.**

`PortraitKey(characterId, variantKey, emotionKey)`가 계약이다.
런타임은 이 키를 `PortraitGeneratedDbSo`에 담고, 툴은 **폴더 구조**에 담는다.
둘 다 같은 키를 답하면 계약은 지켜진다. 저장 방식이 같을 필요는 없다.

`PortraitKey.ToString()`이 이미 `bandi/a/01`을 반환한다.
**키 표현과 경로 규약이 원래 같은 모양이다.**

---

## 2. 수용 기준 — 사람의 동작으로 판정한다

아래 셋에 답하고, 답을 문서에 남긴다.

| # | 시나리오 | 답에 들어가면 안 되는 것 |
|---|---|---|
| S1 | 아티스트가 `bandi`의 새 표정 `07` PNG를 받았다. **툴을 켜지 않고** 프로젝트에 넣는다 | "JSON을 연다" |
| S2 | 배경 `room_night`를 추가한다 | 〃 |
| S3 | 새 캐릭터 `mina`의 초상화 12장을 넣는다 | 〃 |

**답 어디에도 "매니페스트를 편집한다"가 나오면 안 된다.**
매니페스트가 텍스트라서 편집 가능하다는 것은 이 기준을 만족시키지 못한다.
기준은 "가능한가"가 아니라 "비전공자가 안내 없이 하는가"다.

목표 답안:

```
S1: portraits/bandi/a/07.png 로 이름 바꿔서 복사. 끝.
S2: backgrounds/room_night.png 로 이름 바꿔서 복사. 끝.
S3: portraits/mina/a/ 폴더 만들고 01~12.png 로 넣기. 끝.
```

## 3. 할 일

### 3.1 초상화 해석 순서를 바꾼다

`PreviewAssetLibrary.LoadPortraits`:

```
1) 규약 경로 스캔이 1순위
       {portraitsRoot}/{characterId}/{variantKey}/{emotionKey}.png
2) 매니페스트는 2순위 — 규약 경로에 없는 키만 매니페스트의 file로 채운다
3) 둘 다 없으면 기존 폴백((characterId,"a","01")) → Missing
```

매니페스트는 **없애지 않는다.** 런타임 U12 덤프가 자유 경로로 오므로 수입 통로로 남는다.
다만 **권위가 아니라 보조**가 된다.

### 3.2 고아 판정을 좁힌다

현재 규약 위치에 넣은 파일이 고아로 신고된다.

```csharp
// 현재 — 매니페스트에 없으면 전부 고아
if (!referencedFiles.Contains(file)) { orphans.Add(orphan); ... }
```

고아의 정의를 **규약 경로로도 해석되지 않고 매니페스트에도 없는 파일**로 좁힌다.
규약 경로에 맞는 파일은 고아가 아니라 정상 등록이다.

### 3.3 규약 경로 파서를 분리한다

`PortraitKey`에 경로 ↔ 키 변환을 둔다. 문자열 조립이 여러 곳에 흩어지면
원칙 §2.4(규약의 사본 금지)를 어기게 된다.

```csharp
// PortraitKey
public string ToRelativePath(string extension = ".png")
    => $"{CharacterId}/{VariantKey}/{EmotionKey}{extension}";

public static bool TryParseRelativePath(string relativePath, out PortraitKey key);
```

`AssetCoverageModel`의 안내문(§4)과 `LoadPortraits`의 스캔이 **같은 함수**를 쓴다.

### 3.4 안내문을 화면에 노출한다

빈칸에는 **어디에 어떤 이름으로 넣으면 되는지**가 문자열로 보여야 한다.
이것이 이 설계의 사용자 접점 전부다. 드래그 앤 드롭은 이 문자열대로 복사해 주는 편의일 뿐,
드롭으로만 되는 경로를 만들지 않는다.

---

## 4. 만들지 않을 것

| 금지 | 이유 |
|---|---|
| 매니페스트를 편집·생성하는 UI | 매니페스트를 다시 권위로 만든다 |
| 유사 이름 매칭 / 오타 교정 제안 | 규칙이 "이름이 같으면"에서 "툴이 알아서"로 바뀐다 (원칙 §2.3) |
| 규약 경로 자동 정리(일괄 rename) 마법사 | 같은 이유. 사람이 이름을 정하는 것이 규약의 핵심이다 |
| 매니페스트 형식 확장 | 지금 있는 v1로 충분하다. 수입 통로일 뿐이다 |
| 런타임 저장소 수정 | 저장소가 다르다. 필요하면 §6으로 보고 |

## 5. 완료 기준

1. §2의 세 시나리오 답이 문서에 있고, **어디에도 "JSON"이 없다.**
2. `portraits/bandi/a/07.png`를 손으로 넣었을 때
   - 탐색기에 정상 항목으로 뜬다 (고아 아님)
   - `ResolvePortrait("bandi","a","07")`이 `Exact`를 반환한다
   - 매니페스트를 건드리지 않았다
3. 매니페스트로만 오는 기존 항목이 여전히 동작한다 (회귀 없음).
4. 경로 조립 문자열이 코드에 **한 곳**에만 있다.

## 6. 소유자 결정 — 확정 (2026-08-04)

| # | 결정 | 확정 내용 |
|---|---|---|
| 6-1 | U12 내보내기 경로 | **규약 경로로 직접 출력.** `{portraitsRoot}/{characterId}/{variantKey}/{emotionKey}.png`. 매니페스트는 파일 목록 확인용으로 축소, 장기적으로 제거 가능. 런타임 저장소 U12-v1 지시서(`runtime-parallel-orders.md`)가 이에 맞게 개정됨 |
| 6-2 | 배경 하위 폴더 | **허용, 키 = 상대경로.** 현행 `BackgroundAssetEntry`의 `폴더/파일명` 키 구조 유지 — 런타임 `Resources/Backgrounds/{key}`도 key의 `/`를 지원하므로 툴↔런타임 동형. 안내문에 "폴더까지가 키다" 한 문장 추가 |

### 6-1의 이 저장소(VnTool) 쪽 함의

§3.1의 해석 순서는 그대로 유효하다. 매니페스트 2순위는 **구버전 덤프·자유 경로 수입 통로**로 남는다.
새 덤프가 규약 경로로 오기 시작하면 1순위 스캔이 곧바로 집으므로, 툴 쪽 추가 작업은 없다.
