# 깃발(bool 스탯)을 켜는 길 — 작업 지시 · 계약 변경 요청

2026-08-19 · 소유자 결정 · **저작 쪽 구현 완료 · 계약 쪽 대기**

수신: `ked-progression`. 그쪽 [`docs/handoff.md`](../../../ked-progression/docs/handoff.md)
**§6-4 "bool 스탯을 켤 방법이 데이터에 없다"**에 대한 답이다.

---

## 0. 무엇이 문제였나

`met_willow` 같은 깃발은 **선언은 되는데 켜지지가 않았다.**

- `StatChange`는 증감 전용이다.
- 양쪽이 bool 증감을 오류로 막는다 — 이쪽 `VerifyBoolStatUsage`, 그쪽 `VerifyStatChanges`, 둘 다 §G4.
- 그래서 **초기값이 곧 영원한 값**이었다. 조건에서 읽을 수는 있는데 아무도 켤 수 없다.

그 깃발을 보는 관문은 초기값이 거짓이면 **영원히 잠기고**, 그 뒤 에피소드는 도달성 증명에서
도달 불가로 잡힌다. 콘텐츠가 실제로 깃발을 쓰기 시작하는 순간 막히는 자리였다.

> **툴 안에도 같은 모순이 있었다.** 스탯변화 편집기는 bool 줄에 `켬`·`끔` 드롭다운을
> 내놓으면서 시트에는 `+1`·`-1`을 적었고, 리더가 그것을 오류로 잡았다 —
> **툴이 제 손으로 만든 값을 제가 거부했다.** 이번에 같이 고쳤다.

---

## 1. 고른 답 — **지정(Set)**, bool에만

| | 결정 | 근거 |
|---|---|---|
| 어디서 켜나 | **간선** (기존 `스탯변화` 칸) | 아래 §2 |
| 무슨 낱말 | **지정**, 증감이 아니다 | `met +1`은 "만난 횟수"로 읽히고 `+2`는 뜻이 없는데 조용히 같은 결과가 된다 |
| 표기 | `met_willow true` / `false` | `조건` 시트가 bool을 true/false 낱말로 쓰는 것과 같다 — 기획자가 한 낱말만 알면 두 자리에서 통한다 |
| 정수에도 여나 | **아니다** | 줄마다 "더할 것인가 정할 것인가"를 고르게 되면 스탯이 **쌓이는 값**이라는 성질이 흐려진다. 넓히는 것은 나중에 더하기만 하면 되지만 좁히는 것은 깨는 변경이다 |

### 안 고른 것 — Yarn에서 `<<set>>`

**반대한다.** 대본이 값을 바꾸면 **도달성 증명이 그 변화를 볼 수 없다.** "어떤 플레이로도
이 에피소드에 닿을 수 없다"는 보증(§0.5 보증 2)이 통째로 무너진다. 스탯이 변하는 자리가
간선 하나여야 하는 이유는 편의가 아니라 그것이었다.

### 안 고른 것 — 0/1 정수로 두고 `+1`/`-1`

계약을 안 건드려도 되지만, clamp가 의미를 몰래 수행하게 된다. 양쪽 코드가 이미 주석으로
반대해 둔 방식이다.

## 2. 이쪽에서 끝난 것

| | |
|---|---|
| `StatChangeKind { Add, Set }` · `StatDelta.Kind` | ✅ |
| 파서 — `met true` · `met false` · `met = true` 관용 | ✅ |
| 규칙 — bool에 증감 = 오류(**대신 쓸 말을 알려 준다**) | ✅ |
| 규칙 — 정수에 지정 = 오류 | ✅ |
| 규칙 — 한 간선이 같은 깃발을 두 번 정하면 오류 | ✅ |
| 도달성 증명 — 지정은 지금 값을 보지 않는다 | ✅ |
| 스탯변화 편집기 — 켬/끔이 곧 true/false | ✅ |
| **깃발을 쓰는 챕터는 내보내기가 거부한다** | ✅ (§4) |

테스트 15개(`BoolStatSetTests`). 그중 둘이 짝이다 — **깃발을 켜면 잠긴 관문 뒤가 도달
가능해지고, 안 켜면 여전히 도달 불가다.** 뒤엣것이 없으면 "증명이 그냥 다 통과시킨다"로도
앞엣것이 통과한다.

## 3. ⛔ 그쪽에 부탁하는 것 — `StatChange`가 '정하기'를 실을 칸

지금 `StatChangeDto`에는 `Key`·`Amount`뿐이라 **지정을 표현할 자리가 없다.**

제안하는 모양 (이름은 그쪽이 정하는 게 맞다):

```json
{ "Key": "trust",      "Amount": 2 }                    ← 지금 그대로 = 더하기
{ "Key": "met_willow", "Amount": 1, "Op": "Set" }       ← 정하기
```

- **`Op`가 없으면 `"Add"`** — 기존 파일이 한 글자도 안 바뀌고 그대로 읽힌다.
- `Set`일 때 `Amount`는 증감량이 아니라 **정할 값**이다(bool이므로 0 또는 1).
- 불변식 제안: `Set`은 `StatType.Bool`에만 · 값은 0/1만 · 한 간선에 같은 키를 두 번 정하면 오류.
  셋 다 이쪽이 이미 같은 자리에서 막고 있다.

### 도달성 증명 — 알려야 할 동작 변경 (약속대로)

`ApplyChanges`가 `Set`에서 **지금 값을 보지 않고 대입**한다. 증감만 있던 시절 이 함수는
언제나 단조였지만 이제는 아니다.

> ✅ **코퍼스 일곱 케이스에는 지정이 하나도 없어 기존 답은 한 줄도 바뀌지 않는다.**
> 재확인만 하면 되고 다시 쓸 것은 없다. 새 케이스(깃발이 관문을 여는 그래프)를 하나
> 더 뜨는 편이 좋겠다 — 필요하면 이쪽에서 만들어 보낸다.

## 4. 그동안 내보내기는 **거부한다**

깃발을 켜는 간선이 하나라도 있으면 그 챕터의 `progression.json`이 **안 나간다.** 사유가
검증 보고에 선다.

`ViaNodeId`처럼 "저작에만 살고 JSON에는 안 나간다"로 두지 않았다. 그 칸은 빠져도 연출이
안 붙을 뿐이지만, **스탯 변화는 빠지면 게임 로직이 달라진다** — 깃발이 영원히 안 켜지고,
그 깃발을 보던 관문이 영원히 잠기며, 그쪽 도달성 증명이 이쪽과 다른 답을 낸다.
그리고 그 어긋남은 **JSON에 도착한 뒤에는 아무도 볼 수 없다.**

엔딩키 충돌을 저작 쪽에서 막기로 한 것과 정확히 같은 이유다: 값 하나를 잃는 것보다 파일이
안 나가는 편이 싸다.

→ **그쪽에 필드가 서는 날 이 거부 한 함수만 지운다**(`ChapterProgressionExporter.BoolSetNotCarried`).
