## 1. 세 제안 타당성 검토

처음 낸 세 가지를 실측으로 다시 걸었다. **셋 다 방향에는 맞지만, 둘은 범위가 틀렸고
순서도 틀렸다.**

### 제안 ① 뷰에서 저작 정책을 꺼낸다 — ✅ **타당. 범위 그대로**

| | |
|---|---|
| 근거 | `Vn.App` 24,047줄 / 33파일 · **interface 0 · abstract 0 · ViewModel 0**. `ChapterGraphView.axaml.cs` 3,835줄에 `internal` 34개 |
| 피해 실증 | ⑧ 저작 관문을 못 걸었다. 이유가 **`SyncEpisodes()`는 고른 챕터만, `AutoExport()`는 전 챕터**인데 그 사실이 3,835줄 코드비하인드 안에 있어 아무도 못 봤다 |
| 피드백 비용 | `Vn.Authoring.Tests` 760개 **7초** vs `Vn.App.Tests` 327개 **51초** |
| 방향과의 관계 | **저작 정책이 안 보이는 자리에 산다.** 조용한 어긋남을 막는 규율이 정작 자기 코드에서 안 보인다 |

⚠ **MVVM 전면 도입이 아니다.** 꺼내는 것은 *결정*뿐이다: `SyncEpisodes` · `AutoExport` ·
`ValidationFor`(캐시 지문 포함) · 내보내기 거부 장부. 그리기는 뷰에 남는다.

### 제안 ② yarn 실컴파일을 내보내기 경로에 — ⚠ **타당하나 "싸다"가 틀렸다. 둘로 가른다**

| | |
|---|---|
| 근거 | 프로덕션 경로에서 `YarnCompilerAdapter` 호출 **0건**. 테스트에서만 컴파일한다 |
| 방향과의 관계 | **정확히 그 일이다** — 감지기가 있는데 정작 중요한 경로에 없다. 2026-08-23 이름 사건과 같은 모양 |

**틀린 점**: "싸다"고 했는데, `VnProjectAnalyzer.Analyze(yarnProjectPath, schemaPath)`가
**스키마를 요구**한다. 그리고 그 스키마가 **네 번째 사본**이다:

| | 어디 | 무엇 |
|---|---|---|
| `GameDefinition` | `Vn.Authoring/Definition` · `game.definition.json` | 커맨드 팔레트(179항목) · 변수 · 조건 |
| `GameSchema` | `Vn.Core/Schema` · `game.schema.json` · **`internal`** | 커맨드 · 변수 |

같은 어휘의 두 표현이다. 그래서 **둘로 가른다**:

| | 무엇 | 값 |
|---|---|---|
| **②-A** | **빈 스키마로 문법 컴파일만.** 분석기가 스키마 없음을 이미 견딘다(`GameSchema.Empty`) | 문법 오류 + **전역 LineId 유일성(C4)** 회귀를 잡는다. 새 사본 0 |
| **②-B** | `GameDefinition → GameSchema` 유도 — 어휘 사본 제거 | 미등록 커맨드(VN3002)까지. **별건, 나중** |

②-A만으로도 지금 아무도 안 보는 것을 본다. 그리고 툴은 커맨드 어휘를 **이미**
`game.definition.json`으로 저작 시점에 검사하므로, ②-A가 놓치는 구멍은 좁다.

⚠ 이건 `ARCHITECTURE.md:161`의 *"`Vn.App`은 `Vn.Core`를 참조하지 않는다. 두 세계가
갈라져 있다"*를 **의도적으로 넘는 결정**이다. 넘는 이유: 그 분리가 지키려던 것은
"저작 도메인이 Yarn 컴파일러에 묶이지 않는다"인데, ②-A는 **도메인이 아니라 출력 검증**에
쓴다. 도메인(`Vn.Authoring`)은 계속 모른다.

### 제안 ③ `Ked.Presentation.Core` 패키지화 — ⚠ **타당하나 순서가 틀렸다. 둘로 가른다**

| | |
|---|---|
| 실측 (오늘) | 38 같음 · **1 갈림** · 저쪽에만 `Tests/EditMode/` 24파일(정상) |
| 갈린 하나 | `Tuning/PortraitDimensionsDto.cs` — 변형 키 정규화 |

**틀린 점**: 내가 이걸 3순위에 뒀는데, **그 안의 버그는 1순위다.** 다른 항목은 전부
*위험*이지만 이건 **오늘 틀린 답을 내고 있다**:

```
이쪽   변형 키 = 마지막 글자만    'school' → 'l',  'casual' → 'l'   ← 같은 키가 된다
저쪽   변형 키 = 문자열 전체      'school' ≠ 'casual'
```

그래서 가른다:

| | 무엇 | 성격 |
|---|---|---|
| **③-A** | 그 파일 하나 동기화 | **버그 수정.** 지금 · 이쪽 단독 가능 |
| **③-B** | 패키지화 | **재발 방지.** 저쪽이 주인 · 협의 필요 |

③-A 실현성 확인함: 툴의 프로덕션 코드에서 바뀌는 API(`VariantSuffix`·`DefaultVariantSuffix`)를
부르는 곳이 **0건**이다. 손볼 곳은 테스트 하나(`PortraitDimensionsTests.cs:42`)뿐.

## 3. 계획서

### 순서와 근거

```
0  ③-A  코어 사본 하나 동기화        ← 유일한 "지금 틀린 답". 비용 최소
   │
1  ②-A  내보내기에 yarn 문법 컴파일   ← 감지기 구멍. 새 사본 0
   │
2  ①    뷰에서 저작 정책 꺼내기       ← 3의 전제이자 51초→7초
   │
3  ⑧    저작 관문 (대사엔트리 ↔ 노드)  ← 2 없이는 오탐을 낸다
   │
4  ③-B  패키지화 · 저쪽과            ← 재발 방지. 협의 필요
```

**0을 맨 앞에 두는 이유**: 나머지는 전부 *앞으로 생길 어긋남*을 막는 일인데, 이것만
*이미 벌어진* 어긋남이다. 그리고 15분이다.

**3이 2 뒤인 이유**: 관문을 지금 걸면 `SyncEpisodes`(고른 챕터만)와 `AutoExport`(전
챕터)의 어긋남 때문에 **한 번도 안 연 챕터가 전부 거부된다.** 2가 그 둘을 한자리로
가져와야 조건을 바르게 좁힐 수 있다.

### 단계별 완료 정의

| | 완료 정의 |
|---|---|
| **0** | `PortraitDimensionsDto.cs`가 저쪽과 **바이트 일치**(줄바꿈 제외) · `school`≠`casual` 테스트 하나 추가 · 1,490 + α 통과 |
| **1** | 챕터를 저장하면 이미터 출력이 실제로 컴파일되고, 실패하면 **기존 진단 패널에 사유가 선다** · 통과 시 아무 말 없음 · 컴파일 실패는 내보내기를 **막지 않는다**(경고) — 막을지는 실측 뒤 결정 |
| **2** | `SyncEpisodes`·`AutoExport`·`ValidationFor`가 `Vn.Authoring`에 있고 뷰는 결과만 그린다 · 그 셋의 테스트가 `Vn.Authoring.Tests`에서 돈다(7초 대) · `ChapterGraphView`의 `internal`이 34 → 20 이하 |
| **3** | 판이 있고 그 판에 노드가 있는 챕터에서만 검사 · 안 연 챕터는 종전대로 나간다 · 캐시 지문에 노드 목록 포함 · 오탐 0을 테스트가 고정 |
| **4** | 저쪽이 패키지로 떼고 이쪽이 태그로 문다 · 손복사 경로 삭제 |
