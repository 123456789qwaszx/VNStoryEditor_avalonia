## 2. ⚠ 하나의 방향 — 표면과 진짜

### 2.1 표면 (마일스톤)

> 툴이 만든 챕터 JSON을 유니티가 진행 층까지 재생한다 — 선택지가 스탯을 바꾸고,
> 관문이 잠기고, 엔딩이 갈리고, 껐다 켜도 같다.

맞는 말이지만 이건 **다음 마일스톤**이지 방향이 아니다. 이게 방향이라면 셋으로 가를
이유가 없다 — 한 저장소가 더 빨랐을 것이다.

### 2.2 진짜 방향

세 저장소의 문서·주석·거부 코드를 한자리에 놓으면 **같은 문장이 계속 나온다.**

| 자리 | 그 자리가 겁내는 것 |
|---|---|
| `BoolSetNotCarried` (지금은 삭제) | *"JSON은 멀쩡해 보이는데 게임 로직이 달라진다… 도착한 뒤에는 아무도 볼 수 없다"* |
| 엔딩키 충돌 거부 (v14에서 엔딩키와 함께 삭제) | *"조용히 하나를 고르면 나머지가 사라지고 아무도 못 본다"* |
| `ViaNodeId` 키 이름 테스트 | *"틀리면 역직렬화기가 조용히 버려 오류 없이 연출만 사라진다"* |
| 코어 규율 1 (침묵 금지) | *"모르는 것을 조용히 기본값으로 떨어뜨리지 않는다"* |
| `StatChangeDto.Op`가 enum이 아닌 이유 | *"모르는 이름이 기본값 0으로 조용히 미끄러진다"* |
| `CreateInitialState` → `CreateProofEntryState` | *"잘못 부르면 예외 없이 다른 초기값으로 게임이 시작된다"* |
| `SCOPE-BOUNDARY.md` §1 | *"빠진 것을 조용히 두지 않는다"* |
| `ProgressionContentPreflight` | 이름이 갈렸는데 로드·검증·증명은 다 통과했다 |
| `PortraitDimensionsDto` 갈림 | *"오류는 하나도 안 난다"* |

전부 하나다:

> # 🔒 **오류 없이 다른 답을 내는 상태를 없앤다.**

셋의 방향은 "비주얼 노벨을 만든다"가 아니다. **조용한 어긋남의 박멸**이다. 게임은
그 규율이 지켜졌을 때 나오는 결과물이다.

### 2.3 그래서 왜 셋인가 — 분리 자체가 그 방향의 첫 수다

이게 핵심이다. **한 프로그램 안에서는 "둘이 어긋났다"가 아예 표현되지 않는다.**
저작과 재생이 같은 코드면, 어긋남은 버그가 아니라 그냥 동작이다.

```
저작을 밖으로 낸다        →  어긋남이 비로소 표현 가능해진다
규칙을 코어 하나로 만든다  →  어긋날 수 있는 자리를 하나 없앤다
남은 틈에 감지기를 둔다    →  못 없앤 자리를 시끄럽게 만든다
```

**셋으로 가른 것은 비용이 아니라 그 자체가 방어다.** 대가로 "두 산출물이 갈릴 수
있다"는 새 위험을 얻었고, 세 저장소가 지금 하는 일의 대부분이 그 대가를 갚는 일이다.

## 3. 방향을 셋이 어떻게 나눠 지나

같은 적을 **입구·중간·출구** 셋에서 막는다. 다층 방어다.

```
   사람이 적는다              규칙이 판정한다              화면에 나간다
        │                          │                          │
        ▼                          ▼                          ▼
   ┌─────────┐              ┌─────────────┐            ┌──────────────┐
   │ VnTool  │              │ Progression │            │   Runtime    │
   │ 입구 검사│              │  사본 제거  │            │  출구 검사   │
   └─────────┘              └─────────────┘            └──────────────┘
   "실을 수 없으면            "구현이 하나면              "부르는 노드가
    내보내지 않는다"           갈릴 수가 없다"             없으면 시작 안 한다"
```

### 3.1 VnTool — **입구에서 막는다**

사람이 엑셀에 적은 것이 규칙을 어겼는지 본다. 어겼으면 **파일을 안 낸다.**

| 하는 일 | 방향과의 관계 |
|---|---|
| 각 값의 주인을 하나로 고정 (스탯변이=간선 · 이벤트키=에피소드 · 화자=프로젝트) | 같은 사실이 두 시트에 살지 못하게 |
| `ExportValidated` — 오류 있으면 JSON 없음 | **틀린 파일이 하류로 못 간다** |
| 깃발 문법 · 조건 라벨 미등록 거부 | 저작만이 볼 수 있는 어긋남을 저작이 잡는다 |
| 도달성 증명 (완전 탐색) | 사람이 만든 그래프가 갇히는지 저작 시점에 |
| `YarnBundleVerificationTests` — 낸 yarn을 **진짜 컴파일러로** 컴파일 | 산출물을 진짜 소비자로 검증 |

⚠ **입구에서만 막을 수 있는 것이 있다.** 엔딩키 충돌이 그랬다(v14에서 엔딩키와 함께
사라졌지만) — JSON에 도착한 뒤에는 "원래 둘이었다"는 사실 자체가 사라진다. 그런 검사는
하류로 넘길 수 없다.

### 3.2 `Ked.Progression` — **어긋날 자리를 없앤다**

검사하지 않는다. **검사할 필요가 없게 만든다.**

```
[VnTool]  ──┐
            ├──►  같은 static 함수  ──►  같은 답
[Unity]   ──┘
```

| 하는 일 | 방향과의 관계 |
|---|---|
| 조건 평가 · 전이 판정 · 도달성 증명을 한 구현으로 | *"구현이 둘이면 갈린다"* — 실제로 갈렸었다 |
| sans-IO · 인터페이스 0 · async 0 · 값만 주고받음 | 호스트가 달라도 판정이 같다 |
| 로더가 이름 문자열을 검증 (enum 금지) | 모르는 이름이 기본값으로 미끄러지지 않게 |
| 🔒 **"거짓 경보 없음"을 불변식으로 고정** | 증명이 "도달 불가"라 하면 진짜 도달 불가 |
| 성장 규칙 — 표현력 확장 시 *"분석이 못 하는 것을 어떻게 드러내나"* 를 반드시 채운다 | **모르는 것을 모른다고 말할 방법이 없으면 기능을 안 넣는다** |

⚠ 마지막 줄이 이 저장소의 성격이다. 대부분의 코드베이스는 기능을 먼저 넣고 한계를
나중에 발견한다. 여기는 **한계를 드러낼 방법이 없으면 기능을 거절한다.**

### 3.3 `ked-presentation-runtime` — **출구에서 잡는다**

셋 중 **유일하게 두 산출물을 다 본다.** 그래서 마지막 감지기가 여기 있다.

| | 아는 것 | 못 보는 것 |
|---|---|---|
| VnTool | 자기가 낸 `.yarn` 텍스트 | 유니티의 `YarnProject` |
| `ked-progression` | `DialogueEntryId`라는 **문자열** | yarn이 무엇인지 |
| **유니티 호스트** | **둘 다** | — |

| 하는 일 | 방향과의 관계 |
|---|---|
| `ProgressionContentPreflight` — 부르는 노드가 다 있는지 재생 전에 대조 | **2026-08-23의 이름 갈림을 이게 잡았다** |
| `SCOPE-BOUNDARY.md` — 내보낸 기능을 목록으로 유지 | 빠진 것을 조용히 두지 않는다 |
| 세이브를 "경로 저장"에서 "스냅샷"으로 바꿔 돌려받기로 결정 | 대본이 바뀌면 조용히 깨지던 구조를 원천 제거 |
| 등가성 하네스 (`StageStateCapture`) | 순수 코어와 유니티가 같은 그림인지 |

## 5. 한 문단 요약

세 저장소는 비주얼 노벨을 나눠 만드는 것이 아니라, **오류 없이 다른 답이 나오는 상태를
박멸하는 하나의 작업**을 입구·중간·출구에서 나눠 맡고 있다. 저작을 밖으로 낸 것은
어긋남을 *표현 가능하게* 만든 수였고, 진행 규칙을 순수 패키지로 뽑은 것은 어긋날 자리를
*없앤* 수였고, 사전 대조는 못 없앤 틈에 놓은 *감지기*다.

그래서 이 아키텍처의 진척은 기능 수가 아니라 **"같은 사실이 두 곳에 사는 자리가 몇
개 남았나"**로 재는 것이 옳다. 오늘 기준 셋이다.
