## 견본 교체 — 규격 안내 C20의 `!=` 정정 (`85caeb6`)

**한 일** — `docs/chapter-graph-sample.xlsx`를 정정본으로 교체.
이전 견본은 스탯 비교를 "`>=` `<=` `==` `!=` 네 가지"로 적고 있었는데 지시서 §3.1과
`ConditionExpressionParser`는 셋만 다뤄, 견본대로 `!=`를 쓰면 오류가 나는 어긋남이었다.
정정본은 "세 가지 … (`!=` 는 런타임 평가 지원이 확인될 때까지 비범위)"로 적는다.

**확인** — 데이터 5시트(에피소드·간선·조건·스탯·픽스처)는 이전과 동일. 기존 테스트 영향 없음.

**결정 없음** — D7이 이미 정한 대로다. `!=`는 런타임 쪽 확인(B 프롬프트 Q2) 전까지 닫아 둔다.

## Gate A 마무리 — 4항목 전부 닫힘 (`(다음 커밋)`)

그려진 결과를 검증한다. 창을 띄우지 않고, 전역 입력 주입도 쓰지 않는다.
- 견본이 **6노드·5간선**으로 그려진다.
- `branch05.02A`가 `main05.03`보다 **위**에 있다(Y가 작다).
- 엑셀의 간격이 화면에서도 그대로다: X 차 220·440·680, Y 차 240·170. 같은 X를 가진 둘은
  화면에서도 같은 X다(자동 레이아웃이 끼어들지 않았다는 증거).
- 간선이 두 노드의 **중심**을 잇는다.
- 배치 후 카드가 실제 크기(190×74)를 갖는다 — "그려졌다"의 최소 조건.
- 워크북이 없으면 어디에 넣으라고 알려 준다.

**A-3 저장 즉시 갱신 (Gate A 3번).** 감시·디바운스를 뷰에서 떼어내
`ChapterFolderWatcher`(Vn.Authoring)로 옮기고 화면 없이 시험한다.
- 저장하면 알림이 오고 바뀐 값이 읽힌다.

- 엑셀 잠금 파일(`~$…`)은 저장 사건으로 세지 않는다.
- 엑셀이 열어 둔 워크북(공유 읽기·쓰기)도 읽힌다.
- 배타적으로 잠긴 워크북은 재시도 후 **사유를 남긴다**(조용히 빈 챕터가 되지 않는다).

**D12 실제 엑셀 산출물.** 사다리를 순서대로 시도했고 **①②가 모두 없었다**:
Excel COM 없음, LibreOffice 없음(두 경로 다 확인). 그래서 ③에 따라 미확인으로 기록하되,
그 요구가 실제로 막으려던 위험은 다른 방법으로 쳤다 — 아래 "못 닫은 것" 참조.

### 못 닫은 것

- **D12 "Microsoft Excel이 저장한 파일" 픽스처 — 미확인.** 이 기계에 Excel도 LibreOffice도 없어

  숫자 셀·불리언 셀·공유 문자열 워크북을 각각 테스트로 고정. 견본 자체가 openpyxl 산출물이라
  X·Y가 이미 `t="n"` 숫자 셀이어서 숫자 경로는 견본 테스트가 이미 덮고 있었다.

### 스스로 내린 결정

1. **Avalonia.Headless.XUnit을 쓰지 않고 세션을 직접 몬다.**
   근거 — 그 어댑터(12.1.1)는 **xunit v3**를 끌고 오는데 이 저장소는 xunit 2.9.2다. 한 어셈블리에
   둘이 들어오면 `FactAttribute`가 중복돼 테스트 프로젝트 전체가 컴파일되지 않는다(실제로 겪었다).
   `Avalonia.Headless`만 넣고 `HeadlessUnitTestSession`을 직접 쓰면 `[Fact]` 그대로 간다.
   **되돌리는 법** — 저장소를 xunit v3로 올릴 때 `Avalonia.Headless.XUnit`을 넣고 `HeadlessUi`를
   지운 뒤 `[Fact]`를 `[AvaloniaFact]`로 바꾼다. 파일 둘만 만지면 된다.
2. **감시·디바운스를 뷰에서 `ChapterFolderWatcher`로 분리.**
   근거 — 뷰 안에 있으면 창 없이 시험할 수 없다. 파일의 일이지 화면의 일이 아니다.
   **되돌리는 법** — 뷰의 `StartWatching`에 `FileSystemWatcher`를 되돌리면 된다. 다만 그러면
   Gate A 3번이 다시 사람 눈에 의존한다.
3. **노드 카드·간선에 표식(`Tag`)을 단다.**
   근거 — 간선 라벨도 `Border`라서 표식이 없으면 검증이 카드와 라벨을 구별하지 못하고 색·좌표로
   역추론하게 된다. 표식은 읽기 전용이며 쓰기 경로를 만들지 않는다.
   **되돌리는 법** — `Tag` 대입 두 줄을 지우고 테스트를 시각 트리 순서 기반으로 바꾼다(권하지 않음).
4. **빈/실패 상태에서 캔버스 크기를 0으로 되돌린다.**
   근거 — 큰 챕터를 보다가 못 읽는 챕터로 넘어가면 텅 빈 캔버스가 이전 크기로 남아 스크롤만 넓어졌다.
   헤드리스 검증이 이걸 드러냈다(`Measure(NaN)`).
5. **캐시값 없는 수식 셀에 전용 진단을 만든다.**
   근거 — 그런 셀은 파일 안에서 빈 칸이라 그냥 두면 "조건식이 비어 있습니다"가 나가고, 기획자는
   자기 화면에 글자가 보이는데 왜 비었다는지 알 수 없다. 이제 "수식은 있는데 계산된 값이 저장돼
   있지 않습니다 — 엑셀에서 한 번 열어 저장하면 값이 함께 담깁니다"라고 말한다(규칙 14).

## G2-b — 평평화 + `OUT` 자연 수렴 대조 (`(이 커밋)`)

**한 일** — 표를 X11 문법 텍스트로 편다(§3.4).

견본이 `규격 안내`가 그림으로 적어 둔 순서 그대로 펴진다. 산출물을 **글자 하나까지** 고정했다:
`10, 20 → <<if trust >= 3>> 900·905·908 <<endif>> → 40, 50, 60 → 옵션 71(920·928) / 옵션 72`.

**닫은 것 (Gate B 진행분)**

- **같은 대사가 두 번 나오지 않는다** (Gate B 2번). 구간은 이동이지 복제가 아니라 각 LineId가
  정확히 한 번 나온다. 구간의 줄이 원래 자리에서 사라지는 것도 따로 고정했다.
- **§3.3 규칙 6** — `OUT`이 평평화 후의 자연 수렴 지점과 다르면 오류. 선언값과 계산값을
  **둘 다** 메시지에 적는다. 자연 수렴이 없으면 `END`여야 한다는 것도 고정.
- **D6** — 옵션별 `OUT`이 서로 다른 비-`END` 인덱스로 갈리면 오류. 같은 곳으로 수렴하거나
  전부 `END`면 통과.
- `<<if>>` 조립이 `YarnSyntax`를 지난다.

이로써 §3.3 강제 규칙 6개가 **전부** 오류로 잡힌다(1·2·4·5는 G2-a, 6은 여기, 3은 정의).

**스스로 내린 결정**

1. **`CHOICE` 행의 LineId는 평평화 텍스트에 싣지 않는다.**
   Yarn에 "선택 시작"이라는 *줄*이 없다 — 옵션 줄들이 곧 블록이고 머리를 가리킬 자리가 없다.
   §3.2는 `CHOICE`도 라인이라고 하지만(연출·세이브 타깃 가능), 그 신원을 텍스트 경계 너머로
   옮길 그릇이 v1에 없다. 견본의 `ln_0006`이 여기 걸린다.
   모델에는 그대로 읽혀 있어 **데이터가 사라지지는 않고**, 못 싣는다는 사실을 알림으로 남긴다(규칙 14).
   **되돌리는 법** — 기존 툴이 "선택 블록을 여는 줄"을 라인으로 갖게 되면 `EmitOption` 앞에서
   그 줄을 내면 된다. 그전에는 실을 곳이 없다.
2. **진단 메시지에서 한국어 조사(로/으로)를 쓰지 않는다.**
   숫자마다 받침이 달라 "40로"처럼 어긋난 문장이 나갔다. `"실제 수렴 지점은 40입니다"`처럼
   조사가 필요 없는 형태로 쓴다.

**⚠ 다음 단계에서 부딪힐 것 (G3)**

`ScenarioTextParser`는 현재 `->`로 시작하는 줄을 **미해석 목록으로 보낸다**(선택 전환은 그
파서의 비범위다 — 클래스 주석에 명시). 평평화 산출에는 옵션 줄이 있으므로, G3에서 이 텍스트를
그대로 먹이면 선택지가 통째로 미해석이 된다. 이건 기존에 알려진 미결(`composition-node.md`의
K4 "선택지 붙여넣기")과 같은 지점이다. G3 착수 시 다뤄야 하며, 견본 에피소드에 선택지가 있으므로
**Gate B의 "견본이 컴파일되는 텍스트로 나온다"가 여기에 걸린다.**

**테스트 893 통과, 실패 0** (G2-b로 +11).

G2는 여기서 닫힌다. 계획의 G2-c 중 **`#line:` 표기는 평평화에 이미 들어갔고**(산출 줄마다

| 확인한 것 | 결과 |

아니다 — 지만 범위는 파일 넷이다. 이 정정을 기록해 둔다.

## G3-1 — LineId를 텍스트 경계에서 잃지 않는다 (`(이 커밋)`)

**한 일** — `#line:` 신원이 텍스트를 지나 동기화까지 살아서 간다. 조사에서 예고한 대로 파일 넷.

| 파일 | 바뀐 것 |
|---|---|
| `ScenarioTextParser` | 줄 끝 `#line:ln_0001`을 떼어 `ScenarioLine.LineId`로 |
| `ScriptParser`의 `ParsedScriptLine` | `LineId` 자리 신설(기본 null) |
| `ScriptSynchronizer` | **ID 닻**을 내용 닻보다 먼저 쓴다 |
| `ProjectEditor.ApplyScenarioText` | 신원을 그대로 전달 |

**닫은 것 (Gate B)**

- **6번 — 통째 거부되지 않는다.** 같은 대사(`…`)가 세 줄이어도 ID가 있으면 `Ambiguous` 없이
  적용된다. 내용만으로는 확신할 수 없어 거부되던 경우다.
- **3번 — 구간 이동 뒤 LineId 전부 보존.** 순서가 뒤집혀도 새로 발급된 ID가 0개다.
- ID가 같고 문구만 바뀌면 `Modified`이고 신원은 유지된다.
- 신원 없는 새 줄만 새 ID를 받는다.

**회귀 없음** — 태그 없는 텍스트(평평한 대본 붙여넣기)는 내용 매칭 그대로다. 기존 X12 테스트
31개가 손대지 않고 통과한다.

**스스로 내린 결정**

1. **ID 닻이 있으면 내용 닻을 아예 쓰지 않는다**(둘을 섞지 않는다).
   섞으면 같은 줄에 두 근거가 서로 다른 짝을 주장할 수 있고, 그때 무엇을 믿을지 규칙이 하나 더
   필요해진다. 신원을 아는 줄이 하나도 없을 때만 내용 매칭으로 되돌아간다.
   **되돌리는 법** — `FindIdAnchors`가 null을 돌려주게 하면 전부 옛 경로다.
2. **ID가 같은데 문구가 다르면 `Modified`.** 기존에는 닻이 내용으로 잡혀서 닻=같은 문구가
   보장됐고 `Unchanged`/`Moved` 둘뿐이었다. ID 닻에서는 문구가 달라질 수 있으므로 한 갈래를 더 뒀다.
3. **같은 ID가 두 번 나오면 첫 번째만 닻으로 쓴다.** 나머지는 자유롭게 남아 내용 매칭을 타고,
   그래도 확신할 수 없으면 `Ambiguous`로 잡힌다 — 임의로 고르지 않는다(자동 추측 금지).
4. **`#line:` 뒤에 공백이 있으면 태그로 보지 않는다.** 사람이 쓴 "메모 #line: 여기 확인" 같은
   문장을 잘라내지 않기 위해서다.

**남은 것 (G3-2)** — `->` 옵션 줄 해석. 파서가 아직 미해석 목록으로 보낸다. 툴 모델에는
`BeginChoice`·`BeginNextOption`·`EndChoice`가 이미 있으므로 표현할 곳은 있다. 견본 에피소드에
선택지가 있어 **Gate B 1번("견본이 컴파일되는 텍스트로 나온다")이 여기 걸려 있다.**

**테스트 902 통과, 실패 0** (G3-1로 +9).

## G3-2 — 옵션 줄 해석 (`(이 커밋)`)

**한 일** — `ScenarioTextParser`가 `-> 라벨` 줄을 선택 전환으로 읽는다. 기존 미결 K4가 열렸다.

- 첫 옵션은 `BeginChoice`, 뒤따르는 옵션은 `BeginNextOption`(깊이는 늘지 않는다).
- **선택 블록 안에서만 들여쓰기가 뜻을 갖는다** — 들여쓴 줄은 옵션 본문, 들여쓰기가 풀린 줄은
  블록을 닫으며 `EndChoice`를 받는다. Yarn이 옵션 소속을 표기하는 방식 그대로다.
- 옵션 줄도 `#line:` 태그를 갖는다.

**닫은 것 — Gate B 1번의 절반**

**평평화 산출물을 기존 파서가 한 줄도 남기지 않고 읽는다.** 견본을 펴서 `ScenarioTextParser`에
그대로 먹였을 때 미해석 0줄이고, 실린 LineId 전부가 순서까지 그대로 나오며, `BeginIf`·`EndIf`·
`BeginChoice`·`BeginNextOption`이 구조로 잡힌다. **G3가 새 임포터가 아님의 증명**이기도 하다.

**옛 규칙을 고정하던 테스트 하나를 새 규칙으로 다시 세웠다** —
`ScenarioPasteTests.해석_못_한_줄은…`이 `->`를 미해석으로 기대하고 있었다. W47·W54·W55가 같은
자리에서 한 것과 같은 처리다. 남은 미해석은 연출 커맨드와 장식 줄 둘이다.

**스스로 내린 결정**

1. **들여쓰기를 선택 블록 안에서만 읽는다.** 블록 밖에서는 지금까지대로 전부 다듬는다 —
   사람이 붙여넣는 텍스트의 들여쓰기는 대개 뜻이 없기 때문이다. 블록 안에서만은 뜻이 있다:
   버리면 "옵션 본문"과 "블록 다음 줄"을 구별할 방법이 사라진다. 이것이 K4가 열려 있던 이유다.
   **되돌리는 법** — `IsIndented`를 항상 false로 만들면 옛 동작(블록이 안 닫힘)이다.
2. **옵션 줄에 조건 전환이 겹치면 미해석으로 보낸다.** 전환 슬롯은 라인당 하나라는 모델 구조
   때문이다. 어느 쪽도 추측하지 않는다.

**아직 안 닫힌 것 (Gate B 1번의 나머지)** — "**컴파일되는** 텍스트로 나온다"는 파서 통과가
아니라 `.yarn` 실컴파일까지 가야 한다. 파서 → `ApplyScenarioText` → 대사노드 → 이미터 →
`Vn.Core` 컴파일러 경로를 태우는 검증이 남았다. 저장소에 그 경로를 태우는 테스트가 이미
있으므로(`YarnBundleVerificationTests`) 엑셀 출처 노드로 같은 검증을 돌리면 된다.

**테스트 905 통과, 실패 0** (G3-2로 +3, 개정 1).

## G5(핵심) — 에피소드 동기화 서비스 + LineId 되쓰기 + 워크북 생성 (`(이 커밋)`)

**한 일** — 파이프라인 ③→④→⑤가 실제로 한 판으로 이어진다.

- `EpisodeSyncService.Sync` — 워크북 읽기 → 평평화 → `ApplyScenarioText` → 보고.

- **LineId 되쓰기** — 새 행에 발급된 ID가 워크북 B열로 돌아간다. 되쓰기 뒤의 동기화는 변경
  없음(왕복이 닫혔다). 엑셀이 잠갔으면 쓰지 않고 "낡은 상태" 사유를 남긴다.
- **G3-2 보고** — 행이 지워지면 그 줄이 소유하던 전환·set·갈래 출구를 **행별로** 센다.
- `EpisodeLibrary.EnsureWorkbook` — 노드 클릭 시 없는 워크북을 §3.2 규격대로 생성:
  11열 머리글, 유형·태그 드롭다운, **B열 잠금 + 시트 보호**(LineId는 툴 소유), 시작 인덱스 10.
  ClosedXML 도입(D11)의 이유였던 쓰기 경로가 이것이다.

**Gate B 1번 — 실컴파일이 진짜 결함을 잡았다**

`<<if trust >= 3>>`은 Yarn에서 문법 오류다. 챕터 시트의 식은 기획자 언어(스탯키에 `$` 없음,
런타임 `EpisodeCondition` 평가기가 그래프 해금에서 읽음)이고, 대사 안 `<<if>>`는 Yarn VM이
평가한다(브리지가 심는 것이 `$trust`). **두 언어를 잇는 번역기(`ConditionYarnTranslator`)를
한 곳 만들었다** — 식을 다시 해석하지 않고 `ConditionExpressionParser`의 해석 결과를 조립만
한다. `;`(AND) → `&&`, `trust` → `$trust`($ 표기는 `YarnSyntax.NormalizeVariable` 재사용).
`cleared:`는 번역을 거부한다 — 클리어 여부는 Yarn 밖(런타임)의 것이라 대사가 물을 수 없다.

**엑셀 → 노드 → 발행 → 이미터 → Yarn 컴파일러**가 오류 0으로 통과한다(조건 구간 에피소드).

**닫지 못한 것 — 선택지로 끝나는 에피소드는 발행이 막힌다 (소유자 결정 필요)**

툴 모델은 선택 블록을 "내용 있는 후속 줄"(`EndChoice`)로 닫아야 발행된다 — 열린 채면
`PublishRejectedException`(소유자가 테스트로 고정한 규칙: 닫지 않은 블록은 저작 실수 감지).
그런데 §3.4는 "모든 옵션 `OUT=END` → 에피소드 종료"를 정상으로 허용한다 — 후속 줄이 구조적으로
없다. **견본 에피소드가 정확히 이 모양이라 Gate B 1번을 견본으로는 닫을 수 없다.**
발행기 가드를 넓히면(스크립트 끝 = 암묵 닫힘) 기존의 "닫는 걸 잊은" 실수 감지가 죽으므로
임의로 하지 않았다. 선택지:
① 발행기가 "모든 옵션 본문이 스크립트 끝까지 닿음"일 때만 암묵 닫힘 인정
② G8이 옵션 출구(간선 시트의 도착지)를 이을 때 함께 결정
어느 쪽이든 소유자 판단이 필요하다.

**스스로 내린 결정**

1. **동기화가 만든 새 노드의 자동 첫 빈 줄은 은퇴시킨다.** 워크북 줄들은 전부 ID를 실어 오는데
   이 줄만 신원 없는 고아로 남아 동기화가 통째 거부됐다. 손 타이핑용 노드에는 필요한 줄이지만
   엑셀이 채우는 노드에는 설 자리가 없다.
2. **삽입 줄이 신원을 선언하고 오면 그 ID를 그대로 발급한다**(`ScriptSynchronizer`).
   입력이 신원을 밝혔는데 다른 ID를 지어 주면 B열과 대본이 서로 다른 이름으로 갈라진다.

  생긴다(이전의 어색함 해소).

**남은 것**: 챕터 개명/삭제 UI(워크북 파일 개명이라 별도 설계 필요) · 스탯 시트 편집 UI

### 6단계 — 클릭 전수 수리 (소유자 피드백 "클릭이 안 먹힌다", `(이 커밋)`)

**뿌리 결함** — 카드의 PointerPressed가 선택하면서 `Draw()`로 **캔버스를 통째로 다시
만들었다.** 누른 손 밑에서 카드가 파괴되니 ① 더블클릭이 안 먹혔고(둘째 탭이 다른 인스턴스에
떨어짐) ② 드래그가 죽었다(포인터 캡처가 떼어진 카드에 걸림). 셋째로 **간선 라벨**이 히트 선
위에 그려져, 사람이 간선을 누르려고 겨누는 바로 그 자리(가운데)의 클릭을 삼키고 있었다.

**수리**:

- **선택은 다시 그리지 않는다.** 카드·간선을 사전(`_cardById`/`_lineByEdge`)에 기본 스타일과
  함께 등록해 두고, 선택 변경은 `ApplySelectionVisuals()`가 제자리에서 테두리·굵기만 바꾼다.
  캔버스 재구축은 워크북을 다시 읽었을 때(감시·챕터 전환)만 일어난다.
- **간선 라벨 클릭 = 간선 선택.** 라벨을 눌러도 히트 선과 같은 편집 패널이 열린다.
- **빈 판 클릭 = 선택 해제.** 카드·히트 선·라벨이 각자 누름을 소비하므로(`e.Handled`)
  캔버스까지 흘러오는 왼쪽 누름은 진짜 빈 공간뿐이다.
- **오른쪽 단추는 드래그를 시작하지 않는다.** 더블클릭은 둘째 누름이 시작한 드래그 상태를
  걷고 연다(열기와 이동이 겹치지 않게).
- **입력 중 덮어쓰기 방지** — 저장 감시가 다시 그릴 때 오른쪽 패널 글상자에 포커스가 있으면
  그 값을 모델 값으로 덮지 않는다(선택이 바뀌어 채우는 경우는 예외 없이 새 값).
- 패널 목록 줄(간선·조건)의 TextBlock에 투명 배경 — 글자 획 위만 눌리던 것을 행 전체로.

**검증 방식** — 헤드리스 창에 **진짜 포인터 이벤트**(`MouseDown/Move/Up`)를 넣는 클릭 회귀
5건: 클릭해도 카드 인스턴스가 살아 있음(뿌리 결함 고정) · 더블클릭이 워크북을 염(주입 손) ·
라벨 클릭이 간선을 선택 · 빈 공간이 선택을 풂 · 드래그가 엑셀 좌표로 커밋. OS 전역 입력
주입이 아니다 — 창 안의 이벤트일 뿐, 커서는 움직이지 않는다.

**테스트 961 통과, 실패 0** (클릭 회귀 +5).

### 8단계 — 깊이 기반 배치 + 열기 관문 (소유자 피드백, `(이 커밋)`)

**피드백**: ① 에피소드를 열면 챗지피티가 뜬다 ② depth 구분을 명확히 — root의 두 분기가
다시 합류하는 구조가 터무니없어 보인다 ③ 구조부터 검토하라.

**검토 결과 — 데이터 구조는 맞다.** 챕터 = 간선 시트의 DAG이고 합류는 런타임이 그대로
소비하는 정당한 구조다. 잘못된 것은 그 위 두 층이었다:

1. **열기가 OS 연결을 맹신했다.** `Process.Start(UseShellExecute)`는 .xlsx가 무엇에
   연결됐든 그리로 던진다 — 엑셀 없는 기계에서 챗지피티가 가로챘다.
   → `SpreadsheetAssociation`: 열기 전에 기본 앱의 실행 파일을 묻고(AssocQueryString),
   알려진 스프레드시트(엑셀·Calc·WPS 등)가 아니면 **열지 않고** 탐색기에서 파일을 선택해
   보여 주며 사유를 상태줄에 세운다. 모르는 앱은 아니라고 판정한다 — 안전한 방향으로 틀린다.
2. **배치 제안이 국소적·충돌 무지였다.** 부모X+220·형제수×110은 depth 개념이 없어
   같은 열의 두 부모가 만든 자식이 **정확히 겹치고**, 합류 노드가 한쪽 부모 기준으로만
   놓여 간선이 뒤로 꺾였다.
   → `ChapterBranchPlanner`: **열 = 시작에서의 깊이(가장 긴 경로)**, 줄 = 그 열의 빈 자리.
   합류는 가장 깊은 부모 + 1 열. 순환은 깊이 상한(노드 수)으로 가드. 작성기는 계산을
   그만두고 받은 좌표만 쓴다(자리를 아는 것은 그래프 모델이지 워크북 행이 아니다).

**[깊이 정렬] 버튼** — 어지러워진 판을 깊이 열로 다시 세운다. 자동이 아니라 **사람이
누르는 명시 동작**이고(G-2 v2의 자동 레이아웃 금지 유지), 사람 배치를 통째로 덮으므로
삭제와 같은 급으로 `.bak`을 남긴다. 열 안 순서는 현재 Y 순서를 보존하고, 간선 없는
도달 불가 노드는 건드리지 않는다(⚠를 옮겨 숨기지 않는다).

**테스트 979 통과, 실패 0** (플래너 5 · 연결 판정 9 · 정렬 2 · 열기 관문 1).

### 이름 두 종류 + 적던 값이 사라지던 결함 (`(이 커밋)`)

**소유자 보고**: "에피소드 노드에서 정해진 이름을 간선을 클릭한 뒤 직접 바꾸려는데 안 된다."

**진단 — 두 가지가 겹쳤다.**

1. **UI 설계 실수.** 간선 패널 맨 위 `new01 → new02`는 읽기 전용 TextBlock이었다. 이름이
   거기 보이니 거기서 고치려 하는 게 당연한데 고쳐지지 않았다. 게다가 간선을 고르면
   에피소드 패널이 닫혀, 이름을 고치려면 노드를 다시 찾아 눌러야 했다.
   → **양 끝 에피소드를 누를 수 있게** 했다(파란 밑줄 고리, 제목 함께 표시). 누르면 그
   에피소드가 선택되어 `Id [개명]`·`제목`이 열린다. 라벨 칸 안내문도 "선택지 문구 —
   플레이어가 보는 버튼 글자"로 바꾸고 툴팁에 "에피소드 이름이 아닙니다"를 달았다.

2. **진짜 결함 — 적던 값이 조용히 되돌아갔다.** 저장 감시가 울릴 때마다 패널을 모델 값으로
   다시 채웠고, 보호 장치는 "글상자에 포커스가 있는가"뿐이었다. 콤보·체크박스를 만지거나
   마우스만 옮겨도 뚫렸다 — 이름을 적어 두고 조건 콤보를 고른 뒤 [적용]하면 이름이 원래대로
   돌아가 있었다. 사람 눈에는 **"적용을 눌러도 안 바뀐다"**.
   → 포커스 판정을 버리고 **선택이 바뀔 때만 편집 칸을 채운다**(`_panelFilledFor`).
   목록(ItemsSource)은 계속 새로 고치되 고른 값은 지킨다(`SetItems`).

**조용한 무동작도 없앴다** — [적용]의 가드가 걸리면 아무 말 없이 돌아가던 것을, 사유를

### 오른쪽 패널을 탭으로 — 조건이 앞 탭 (`(이 커밋)`)

끌어내지 않는다.

조건 탭에 안내 두 줄을 넣었다 — "식은 한 번만 정의하고 라벨로만 부른다"와, 식 칸 툴팁의

### 소유권 확정 — 툴은 형태, 엑셀은 값 (`(이 커밋)`)

**소유자 고민**: "제목·엔딩키처럼 툴에서 조작할 필요 없는 건 엑셀에서 하고 툴은 읽기
전용으로 해야 하나? 표시/해금조건도 사실 엑셀이 맞을 수도."

**선을 그었다 — 툴은 그래프의 형태(참조), 엑셀은 값(내용).**

| 툴이 쓴다 | 엑셀이 쓴다 |
|---|---|
| 에피소드 생성·삭제·개명, 간선 연결·삭제, 간선의 선택지 문구·조건·잠김 | 제목 · 엔딩키 · 표시/해금조건 · 인덱스 · 종류 · 대사엔트리 · 메모 · 도달불가 허용 · 조건식 |

근거는 **틀렸을 때의 대가**다. Id 참조는 손으로 맞추면 오타 하나가 유령 간선이 되고 시트
두 곳을 오가야 한다 — 툴이 한 저장으로 맞춰 준다. 값은 그냥 글자라 엑셀이 더 낫다
(복사·채우기·되돌리기가 다 있다).

**표시/해금조건을 엑셀로 내리기 전에 드롭다운을 먼저 깔았다.** 툴 콤보가 유일한 오타
방지책이었으므로 그냥 내리면 "라벨 오타 → 검증 오류"를 사람이 반복해 만난다. 새 챕터
워크북의 `표시조건`·`해금조건`·간선 `조건` 열은 이제 **`조건` 시트 라벨 열을 가리키는 범위
참조 드롭다운**이다 — 정적 목록이 아니라서 조건을 더하면 목록이 따라온다. 에피소드
워크북의 `유형`·`태그`에 이미 쓰던 방식이다.

**패널에서 뺀 것**: 제목·엔딩키 칸, 표시/해금 콤보, [적용] 버튼. 대신 **엑셀 소유 값을
읽기 전용 한 덩어리로** 세운다(제목·대사엔트리·표시/해금·엔딩키·엑셀 행 번호 + "이 값들은
엑셀에서 고칩니다"). 확인하러 엑셀을 열 필요는 없되, 고치는 자리가 어디인지는 분명하다.

**새 노드는 제목 없이 만든다.** 제목이 카드에 표시되는 글자라, 툴에서 못 고치게 하면서
"새 에피소드"로 채우면 그래프가 같은 이름의 벽이 된다. 제목이 비면 카드가 Id를 굵게
보여주므로(중복 줄은 생략) 그래프가 읽힌다 — 제목은 엑셀에서 나중에 붙이는 장식이 된다.

**남은 편집 탭**: `Id [개명]` · 엑셀 소유 값(읽기 전용) · 다음 에피소드 목록 · [연결] ·
[에피소드 삭제], 그리고 간선 패널.

**테스트 977 통과, 실패 0** (+1 드롭다운, 패널 테스트 2건 개정).

### 한 구간에 선 하나 — 레일은 입구까지, 속은 작가의 배선 (소유자 보고, 2026-08-15, `(이 커밋)`)

### (진행) 합류 — 확장한 커스텀 웹이 돌아가는 자리가 보인다 (소유자, 2026-08-15, `(이 커밋)`)

  "출구 없음 = (진행) — 에피소드가 끝나고 다음은 챕터 간선이 정합니다."

**규격 v6**:

- **간선**: `선택지`(문구) 열이 **`선택지수`**(정수, 기본 1, 드롭다운 1·2·3)가 됐다.

  간선(출발→도착)이다. 대본 text는 **자유 수정**(신원이 아니라서 언제 고쳐도 배선이

- **자동 칸 생성**: 간선 추가(툴 [연결]·[＋ 에피소드])가 빈 칸 하나를 함께 만들고,

  ("공간이 생기도록" — 모자란 칸이 없으면 파일에 손대지 않는다). 삭제·개명은 칸이

- **간선의 대표 문구는 파생값**: 리더가 그 간선 칸들의 첫 보이는 text를 `OptionLabel`에

  선택지 시트로 교체(칩 문구 = 칸의 대본 text, 클릭 = 주인 간선 선택).
- **내보내기**: NextOption이 칸 단위다 — 보이는 칸마다 하나(문구 = text), 전부 빈 간선은
  라벨 빈 문자열 하나(보이지 않는 기본). 조건·잠금·스탯변화는 간선 것. 스키마 불변.

### 선택지 v7 — 에피소드가 칸 수를 정하고, 간선은 칸과 1:1 (소유자 정정, 2026-08-16, `(이 커밋)`)

**소유자** — "선택지수가 간선에 있으면 안 된다. 간선에는 선택지가 하나 대응되는 거고,
에피소드에서 선택지의 숫자를 지정하면 그 숫자만큼 간선이 생겨야 한다. 선택지 시트에는
도착이 필요 없다 — 인덱스만 어떤 문구를 가져올지의 정보로 필요하다. 근원노드(출발
에피소드)에서 Choice를 하나 만드는 게 시작이고, 그 아래 Option을 기본 1칸 둔다."

v6에서 내가 칸의 주인을 간선으로 잡았던 것을 바로잡는다:

- **에피소드 시트에 `선택지수`(K열)** — 그 에피소드 끝 Choice의 Option 칸 수(기본 1).
  동기화 `TopUpChoiceSlots`가 이 수만큼 칸을 만든다(넘치는 칸은 안 지운다 — 원고 보호).
- **`선택지` 시트에서 도착 폐지**: 출발 | **인덱스** | 대본 | 메모. 인덱스가 칸의 신원이고,
  칸이 갖는 것은 순서와 자유 수정 대본 text뿐이다(조건·도착 등은 전부 간선 소유).
- **간선 D열 = 짝 칸의 인덱스**, 신원 = (출발, 인덱스). 같은 도착으로 문구 여럿도 된다
  (인덱스가 다르니 다른 길). 같은 칸을 둘이 가리키면 오류.
- **칸은 미리, 간선은 이을 때** (소유자 선택): 선택지수를 올리면 칸만 서고, 도착을 고르는
  순간 간선이 생긴다. 안 이은 칸은 검증이 "간선이 없습니다"로 짚는다.
- **툴 편집 탭이 선택지 목록이 됐다**: 줄 = 칸(`10 · 문구 → 도착`), [＋] = 칸 추가
  (선택지수 +1), 줄 클릭 = 그 줄 아래에서 도착 잇기/바꾸기, ✕ = 칸 삭제(이어진 간선도).
  안 이은 칸은 "아직 안 이음", 빈 대본은 "(기본 · 보이지 않음)"으로 보인다.
  간선 패널의 선택지 칸은 읽기 전용 표시다(문구는 엑셀에서).
- **시각 폴리싱**: 선택지 시트는 구조 열(출발·인덱스) 회색 + 대본 열 넓게 + 머리글 고정.
  목록의 칸 번호는 칩으로(이은 칸은 호박, 안 이은 칸은 회색).
- **Migrator v7**: v5(간선에 문구)·v6(칸에 도착 + 간선에 선택지수) 어느 쪽에서 와도
  칸 인덱스 짝으로 모은다. v6 칸은 도착 열만 지우고 대본을 그대로 물려받는다.
  에피소드 `선택지수`는 실제 칸 수로 채운다. 견본 재이행 완료.

### 챕터별 대본 격리 — 같은 이름이 서로를 덮지 않는다 (소유자 보고, 2026-08-16, `(이 커밋)`)

고침 — 둘 다 **챕터 범위**로 좁혔다:

- 대본은 `episodes/{ChapterId}/{EpisodeId}.xlsx`에 산다. 챕터 워크북이
  `chapters/{ChapterId}.xlsx`인 것과 같은 결이다. 열기·생성·개명·삭제·검증·내보내기·
  화자 전파·대사 미리보기가 전부 그 챕터 폴더 하나를 지난다(`SelectedEpisodesFolder`).

- 폴더 감시는 `IncludeSubdirectories`로 하위 폴더의 저장까지 잡는다.

**구판 원고 입양** — 뿌리에 평평하게 있던 파일은 동기화 때 그 챕터 폴더로 **옮긴다**.
단 **주인이 하나일 때만**: 여러 챕터가 같은 EpisodeId를 쓰면 어느 원고인지 알 수 없으므로
손대지 않고 "직접 옮기거나 이름을 나눠 달라"고 말한다(남의 원고를 가져오지 않는다).

**되돌리는 법** — 이 커밋 revert 후 `episodes/{챕터}/*.xlsx`를 뿌리로 도로 옮긴다.

고정: 같은 이름이 챕터마다 다른 파일을 갖고 한쪽 수정이 다른 쪽에 안 번진다 · 챕터 폴더는
서로의 파일을 못 찾는다 · 입양(주인 하나면 이동, 여럿이면 경고 후 보존) · 동기화가 자기 판의

### 대사는 흐르는 글이다 — 카드 철회 + 탭 속의 탭 제거 (소유자 재지시, 2026-08-16, `(이 커밋)`)

### v9 — 선택지 시트가 챕터 전체의 문구 사전이 됐다 (소유자 지시, `(이 커밋)`)

**소유자** — "간선 시트의 선택지는 지금처럼 인덱스를 가져오는 게 아니라, 그냥 깡으로

쓸 수 있도록 할 거야. 선택지 시트에서도 출발노드는 제거하고, 선택지의 대사와 인덱스만
있으면 될 것 같아. 특정 에피소드에서 선택지를 고를 때 자기 것만 고르는 게 아니라, 모든
선택지 중에서 자유자재로. 이건 어차피 그냥 보여주기용 라벨일 뿐이야."

**바뀐 것 — 값의 주인이 옮겨졌다:**

| | v7·v8 | **v9** |
|---|---|---|
| `선택지` 시트 | 출발·인덱스·대본·메모 (에피소드의 칸) | **인덱스·대본·메모** (챕터의 문구 사전) |
| 간선 `선택지`(D) | 짝 칸의 **인덱스** | **문구 그 자체** |
| 간선 신원 | (출발, 인덱스) | **(출발, 도착, 문구)** |
| `에피소드` 선택지수(I) | 칸 수를 선언 | **폐지** — 나가는 간선 수가 곧 선택지 수 |
| 보이지 않는 기본 | 빈 대본 칸과 짝인 간선 | **문구 없는 간선** |

핵심은 사전이 **배선이 아니라 어휘집**이라는 것이다. 간선이 인덱스로 참조하지 않고 문구를
직접 적으므로, 사전에서 낱말을 지워도 이미 쓰인 문구는 살아 있고 아무 길도 안 쓰는 낱말이
남아 있어도 잘못이 아니다. `조건` 시트가 라벨↔식 사전인 것과 같은 자리다.

**파생 결정 둘** (소유자에게 물어 확정):

- **`선택지수` 폐지** — 칸이 사라졌으니 셀 것도 없다. [＋]는 이제 "칸 추가"가 아니라
  **빈 폼 열기**이고, 문구와 도착을 고르는 순간 길이 생긴다.
- **같은 도착으로 문구 여럿 허용** — 신원이 (출발, 도착, 문구)라 "믿는다"·"무시한다"가
  둘 다 ep05로 가되 스탯변화만 다른 흔한 패턴이 그대로 선다. 셋이 다 같으면 오류.

**검증은 줄었다.** 칸 짝·칸 수 검사가 통째로 사라지고 `VerifyPlainAdvances` 하나가 남는다:
문구 없는 간선은 에피소드당 하나뿐이고 그 길에는 관문이 없어야 한다(그것마저 잠기면 갇힌다).
대신 리더에 경고 하나를 더했다 — **같은 에피소드에서 같은 문구가 여러 갈래**로 가면
플레이어에게는 같은 버튼 둘이다(막지는 않는다: 사람이 판단할 일이다).

**화면.** 편집 탭의 줄이 칸이 아니라 길이 됐다(`문구 → 도착 [조건]`). 폼은 그대로 한 줄
`[선택지 ▾] → [도착 ▾] [수정]`이되 문구 드롭다운이 **챕터 전체**를 담는다. 카드 오른쪽
포트도 문구 붙은 간선에서 곧장 온다 — 주인 없는 빈 원이 사라졌다(포트가 곧 길이다).
엑셀 쪽 간선 D열 드롭다운은 사전의 대본 열(`선택지!$B$2:$B$200`)을 통째로 가리킨다.

**이행.** v5(간선 D = 문구, 시트 없음)는 칸으로 만들었다 되돌리는 왕복 없이 곧장 사전으로
간다 — 문구가 온전하려면 그 편이 옳다. v6·v7·v8(출발 열 있는 시트)은 (출발, 인덱스) → 대본
맵을 떠서 간선 D에 문구를 새기고, 사전을 중복 없이 다시 짓는다(빈 대본 행은 걷어낸다).
견본 `docs/chapter-graph-sample.xlsx`도 이행해 커밋했다.

### 간선 패널에서도 선택지를 고른다 + v9 문구 정리 (소유자 지시, `(이 커밋)`)

드롭다운**이고 [적용] 한 번에 관문·스탯변화와 **함께** 저장된다 — `UpdateEdge`에

**② 사전을 에피소드의 것으로 알던 쓰기 둘을 걷었다.** `RenameEpisode`가 선택지 시트 A열을
새 Id로 바꾸고 `RemoveEpisode`가 그 에피소드의 칸을 지우고 있었다 — v9에서 A열은 인덱스라

(고정: 에피소드를 지워도 그 문구는 사전에 남는다.)

**③ 문구 갱신** — "칸"이라는 말이 남아 있던 자리를 v9 어휘로:

  "**문구는 챕터 사전에 남습니다 — 다른 길에서 다시 씁니다**"

### 시나리오 그래프 v9 — 가지의 주인이 대본에서 챕터 간선으로 (소유자 보고, `(이 커밋)`)

**소유자** — "시나리오 그래프에서 보고 있는데, '이 문구의 Option이 대본에 없습니다'라면서
레거시의 그런 느낌이야. 시나리오 그래프도 최신화 해줄래?"

**원인은 뒤집힌 주인.** 철도(T2)는 **대본의 OPTION 줄**이 가지를 만들고 챕터 간선이 문구로
짝을 찾는 구조였다. v9에서 선택지의 주인이 챕터로 왔고 **대본에 OPTION이 없는 것이 정상**이
되면서, 모든 간선이 짝을 못 찾아 "유령"(흐린 칩 + 저 경고)으로 그려졌다.

**뒤집었다.** 가지 하나 = **간선 하나**이고, 순서는 간선 시트의 행 순서다. 유령이라는 개념이
사라졌다. 대본에만 남은 구판 OPTION 줄은 반대로 **스텁**이 된다(그 길은 여기서 끝난다) —
"챕터에 이 선택지가 없습니다"로 사실만 말하고 지우라고 강요하지 않는다.

읽는 순서는 지켰다: ① 문구 있는 길(시트 행 순서) ② 구판 OPTION 스텁 ③ 문구 없는 진행.
진행이 맨 아래인 것은 2026-08-15 소유자 보고("진행이 선택지 위에 서니 헷갈린다") 때문이고,
보이지 않는 기본은 플레이어에게 버튼으로 안 뜨므로 선택지 순서를 왜곡하지도 않는다.

**작가의 배선이 매달릴 자리를 새로 냈다** — `ExitPortKind.Choice` + `DialogueNode.ChoiceExits`
(**문구 → 자유 씬**). 예전에는 OPTION 줄의 LineId가 열쇠였는데 그 줄이 없어졌으므로,
v9에서는 **문구가 열쇠**다. `BranchExits`와 달리 대본 편집의 줄 청소(`PruneBranchExits`)에
쓸리지 않는다 — 문구의 주인은 챕터라 대본이 바뀌어도 그대로여야 한다. 판 파일에는
`choiceExits` 항목으로 산다(줄 항목 안이 아니라 노드에 따로 — 열쇠가 줄이 아니니까).
구판 대본에 OPTION 줄이 남아 있고 문구가 같으면 **그 줄의 포트를 그대로 쓴다**(옛 배선 보존).

**⚠ 열린 채로 둔 것 — 내보내기.** 이 배선은 저장되지만 **아직 내보내기에 실리지 않는다**:
발행 경로(`DialoguePublisher`)의 점프는 대본의 줄에 매여 있어 문구를 열쇠로 한 점프를 실을
자리가 없다. v9 전이 규칙 자체가 런타임 계약(Gate D) 개정을 기다리는 중이라 같은 항목이다.
칩 상세에 그 사실을 적어 두었다 — 저장됐는데 안 나가는 것을 모르는 편이 더 나쁘다.

고정: 대본에 OPTION이 없는 챕터에서 간선마다 칩이 서고(흐림 없음), 문구를 열쇠로 자유 씬을
달면 철도가 그 카드로 진입하며, 판 파일 왕복 뒤에도 배선이 남는다.

**테스트 1070 통과, 실패 0** (Ked 220 · Core 60 · Authoring 615 · App 175).

### Gate D 개정안을 계약서로 확정 — 저작이 내는 것 ↔ 런타임이 못 읽는 것 (`(이 커밋)`)

v9까지 오면서 "런타임 계약(Gate D) 개정 필요"라는 꼬리표가 여러 항목에 붙었는데, **무엇을
어떻게 고쳐야 하는지가 어디에도 한데 적혀 있지 않았다.** 유니티 쪽에 넘길 수 있는 형태로
`docs/runtime-contract.md`에 **§G 챕터 진행 JSON — 수입기 계약**을 새로 썼다. A~F는 `.yarn`
텍스트의 계약이고, G는 `exported/{챕터}.progression.json`이라는 **다른 표면**이다.

**추측이 아니라 실제 출력에서 옮겼다** — 스크래치로 챕터를 하나 지어 내보내고 JSON을 눈으로
확인했다. 그 과정에서 문서 초안의 오류도 하나 잡혔다: 키가 camelCase인 줄 알고 적었는데
**실제 출력은 PascalCase**다(수입기가 그대로 믿으면 전부 null이 됐을 자리).

조용히 어긋날 자리 넷:

- **G2 — `IntValue`는 0이면 키 자체가 없다.** `JsonIgnoreCondition.WhenWritingDefault`라
  `trust >= 0`은 `{Kind, Key, Op}`만 나간다. 수입기가 없는 키를 0으로 안 읽으면 **bool 조건
  (`flag == false`)이 통째로 어긋난다** — 가장 흔한 조건인데도.
- **G3 — 새 Op 둘**(`GreaterThan`·`LessThan`)이 이미 나가고 있다. 런타임 enum에 없다.
- **G5 — 관문이 노드에서 길로 내려왔다**(v8). `Node.VisibleConditions`는 언제나 빈 배열이고
  값은 `Option.VisibleConditions`에 있는데, **런타임 `EpisodeNextOption`에 그 필드가 없다.**
  Gate D의 가장 큰 한 칸.
- **G7 — 스탯의 초기값·최소·최대가 어느 런타임 입력에도 없다.** progression JSON에도
  `game.definition.json`에도 없음을 코드로 확인했다. 그런데 툴의 도달성 증명은
  `Math.Clamp(값, 최소, 최대)`로 걷는다 — **증명과 실제 플레이가 갈릴 자리**다.

G7·G8(선택지별 자유 씬 점프)은 **저작 쪽 페이로드를 바꿔야** 닫힌다. 외부 팀과의 계약이라
혼자 바꾸지 않고 §F 소유자 확인 항목에 6·7·8번으로 올려 두었다 — 권고안까지 적었으니
결정만 내리면 저작 쪽은 한 번에 고친다.

고정: `수입기가_믿어야_하는_JSON_규약을_고정한다` — G2(0이면 키 없음)·G3(GreaterThan)·
G5(노드 빈 배열, 길이 소유)를 실제 JSON으로 못 박는다. 여기가 깨지면 계약서도 함께 고친다.

**테스트 1071 통과, 실패 0** (Ked 220 · Core 60 · Authoring 616 · App 175).

### 두 계층을 화면에서 가른다 — 조건·변수·화자 (소유자 지시, `(이 커밋)`)

**소유자** — "시나리오 설정노드의 조건, 변수, 화자와 챕터 그래프에서 챕터엑셀의 조건, 변수,

**섞여 있던 것을 코드로 확인했다.** 2026-08-15의 A계층 격리는 **카드와 공급 링크만** 숨겼고,
값 자체는 작가의 목록에 그대로 흘러들고 있었다:

- **조건** — 챕터 조건이 `챕터 {판} 조건` 공급 설정노드로 주입되는데, `AvailableConditionResolver`는

  나란히 뜨고 구분이 없었다.
- **변수** — 챕터 `스탯` 시트는 `game.definition.json`의 `variables`를 거울로 삼는데, 작가의
  변수 후보가 **그 목록 통째**였다. 즉 작가가 `trust`에 `<<set>>`을 걸 수 있었다 —
  **"스탯이 변하는 자리는 간선뿐"이라는 규칙이 화면에서 지켜지지 않고 있었다.**
- **화자** — 챕터 `화자` 시트(A계층 등록)와 정의 파일 speakers(초상화 매핑)가 따로 살고,

**소유자 결정대로 셋을 각각 다르게 처리했다:**

| | 처리 | 왜 |

| 조건 | **고르는 목록에서 뺀다** | 골라도 값의 주인은 챕터라 못 고친다. 단 **이미 쓰인 것은 읽힌다** — 숨겨서 "알 수 없는 조건"이 되면 그게 더 나쁘다. `[기획] 신뢰높음`으로 출처가 이름에 붙는다 |

| 화자 | **합치되 구역을 가른다** | 자유 씬에서도 챕터 등록 화자를 쓰는 것이 자연스럽다. 드롭다운이 `기획 등록 · 챕터 화자 시트` / `초상화 매핑 · game.definition.json` 두 구역으로 선다 |

### game.definition은 기획자 전용 · 작가 조건·변수는 챕터 전역 (소유자 지시, `(이 커밋)`)

**소유자** — "game.definition부터 제대로 세우자. 이게 기획자가 쓰는 전용으로 되어야 하는데,
현재는 시나리오 작가가 한것까지 저기에 들어간다. 작가가 만든건 굳이 json으로까지 저장될
필요는 없어보여. 또 지금 조건노드를 개별 대사노드에 연결시키는데, 작가가 만든 조건·변수는
챕터 단위로 기록이 되어서 사용됐으면 해. 이거는 챕터단위로 전역에 쓰이는거야."

**셋을 함께 고쳤다.**

**① 공급 범위가 개별 링크 → 판(챕터) 전체.** `ConnectedSetNodeResolver`가 Settings link
대신 **같은 판의 SetNode 전부**를 준다. 판 = 챕터 1:1이므로 그게 곧 챕터 전역이다.
- 동기화가 대사노드마다 링크를 잇던 고리 폐지 — 노드를 만들 때마다 배관을 다시 잇지 않는다
- 그래프에 조건 공급선을 안 그린다 — 범위가 판 전체라 선을 그리면 노드 수만큼 거미줄이
  되고, 그 선이 무엇을 정하지도 않는다. SetNode 포트는 "이 챕터에 공급 중" 표시로만 남는다
- 구판 프로젝트의 링크 데이터는 지우지 않고 조용히 무시한다
- "못 쓰는 조건"의 뜻이 바뀌었다: **다른 챕터에 있다**. 문구도 그렇게 고쳤다

**② `game.definition.json`은 기획자 전용이 됐다.** 작가 화면(설정노드)이 정의 파일의
speakers를 갈아 끼우던 길(`AuthoringSession.SaveSpeakers`)을 걷어냈다. 이제 정의 파일에
쓰는 창구는 **기획자 화면의 [등록] 하나**뿐이다(챕터 그래프 검증 보고의 변수 등록).

**③ 화자는 두 묶음으로 갈렸다** (소유자 설계 그대로):
- **기획자가 정한 화자는 회색 고정** — 모든 조건노드에 함께 서되 이름·캐릭터키가 잠긴다.
  있다는 것을 알아야 이름이 겹치지 않는다
- **표정은 누구든 자유롭게** — 표정의 주인은 에셋 폴더 규약이지 정의 파일이 아니라서
  애초에 계층 문제가 없었다(확인함). 잠긴 줄에서도 [표정]은 살아 있다
- **작가가 더한 화자는 프로젝트에 산다** (`StoryProject.WriterSpeakers`, manifest의
  `writerSpeakers`) — 정의 파일이 아니다. 없어도 대본은 돈다: 화자 칸은 자유 입력이고
  이 목록은 편의일 뿐이다. 대사노드 드롭다운은 세 구역(기획 시트 · 초상화 매핑 · 작가)

**앞선 커밋에서 놓쳤던 구멍도 메웠다** — 설정노드의 **배정**은 `Set_` 노드 본문이 되어
실제로 `<<set>>`이 나가는데, 스탯 경고가 **대사 줄만** 훑고 있었다. 변수 후보에서 뺐어도
손으로 적으면 조용히 새어 나갔다. 이제 배정도 검사한다.

고정 8개(계층 분리 5 + 챕터 전역 3): 같은 판의 모든 설정노드가 공급한다 · 다른 판 것은

### 설정노드는 챕터의 컨트롤러다 + 챕터 화자 반영 버그 (소유자 지시·보고, `(이 커밋)`)

**소유자** — "이렇게 되면 조건 노드라기보다는 챕터별로 자동으로 저장되는 컨트롤러에 가까운
것 같아. 조건 노드 추가 및 삭제는 제거하면 될 것 같아. 챕터 하나에 저런 설정을 담아두는

화자목록이 있는데 반영이 안되네."

**① 설정노드가 컨트롤러가 됐다.** 앞 커밋에서 공급 범위를 판(챕터) 전체로 넓히고 나니
**여러 개일 이유가 없어졌다** — 어차피 다 같은 곳에 미치므로 나눠 놓으면 "어디에 적었더라"만
생긴다. 소유자 말이 맞다.

- **챕터마다 하나가 자동으로 선다** (`ProjectEditor.EnsureChapterSettingsNode`, 이름 `{챕터} 설정`).

- **[+ 설정 노드] 폐지** — 만드는 것이 아니라 딸려 있는 자리다
- **삭제도 막았다** — 지우면 그 챕터의 조건·변수가 통째로 사라지고, 어차피 다음에 판을 열

- A계층 공급 노드는 세지 않는다 — 그건 기획자 자료를 나르는 배관이라 따로 산다

대사노드 드롭다운은 세 원천을 다 보는데 설정노드만 하나를 못 본 것이다. 이제 시트가 먼저
서고(등록의 주된 자리), 같은 이름은 한 번만 센다. 캐릭터키는 정의 파일이 알고 있으면 그걸
붙인다 — 초상화 매핑의 주인은 여전히 정의 파일이다.

### 작가가 쓰는 건 변수가 아니라 아이템·능력이다 (소유자 지시, `(이 커밋)`)

**소유자** — "시나리오 작가가 쓰는건 변수라기 보다는 아이템이라고 하는게 맞겠다.
아이템 혹은 능력."

이름이 뜻을 말하지 못하고 있었다. `float (숫자)` / `bool (플래그)`는 **자료형 이름**이라
작가에게 아무것도 설명하지 못한다 — 무엇을 담는 칸인지가 안 보였다. 소유자의 어휘가
그것을 그대로 메운다:

| | 전 | 후 |
|---|---|---|
| 묶음 이름 | `변수 값` | **`아이템 · 능력`** |
| 종류 | `float (숫자)` · `bool (플래그)` | **`아이템 (개수)`** · **`능력 (보유)`** |
| 이름 칸 | `변수` | `아이템·능력 이름` |
| 대사 줄 드롭다운 | `등록 변수 없음` | `등록된 아이템·능력 없음` |

**저장되는 자료형은 그대로 `float`/`bool`이다** — 바뀐 것은 이름뿐이라 옛 프로젝트도
그대로 읽히고 Yarn 출력도 바이트 단위로 불변이다. 개념을 갈아 끼우려고 데이터를 이사시킬
이유가 없다.

**아이템은 개수로 늘고 줄고, 능력은 있다/없다뿐이다** — 이 한 줄이 안내문이 됐다. 예전
안내문은 "정의 파일이 제안하는 변수 N개"였는데, 그건 **어디서 오는가**만 말하고 **무엇인가**를
말하지 않았다.

조건으로 쓰는 길은 그대로다(소유자 결정) — 설정노드에서 조건을 따로 적고 대사 줄에서 고른다.

**테스트 1081 통과, 실패 0.**

### 아이템·능력은 챕터 단위로만 산다 — 네임스페이스 + 정의 파일 차단 (소유자 지시, `(이 커밋)`)

**소유자** — "아이템, 능력은 오직 챕터단위로만 살리는게 맞아. 왜냐면 이건 짧은 스토리 단위를
상정한거야. 스토리 게임이고 시나리오와 챕터가 꼭 연관되어있으리라는 법은 없어. 그런데 그게
이렇게 널부러지면 곤란해. / 애초에 game.definition.json에서 오는 기획자용 스탯은 시나리오
작가에게 노출되어서는 안돼. 오직 화자의 경우에는 캐릭터이름이 그대로 쓰이니 예외적으로."

**⚠ 내 제안이 틀렸다.** "런타임 변수가 전역이니 저작도 전역이어야 한다"고 권했는데 인과가
거꾸로였다 — 런타임의 전역성은 **제약**이지 설계가 아니다. 짧은 스토리 단위를 상정하면
아이템이 챕터를 넘어 널브러지는 쪽이 사고다. 그리고 이 저장소는 **이미 답을 정해 뒀었다**:
`chapter-graph-orders.md` §0.5 "구멍 A — 이름 충돌"의 해법이 **자동 네임스페이스**다.

**① 새 저장소를 만들지 않았다.** 설정노드가 곧 챕터 단위 저장소다 — 챕터당 하나가 자동으로
서고 그 안의 아이템·능력은 그 챕터에서만 산다. 더 둘 자리가 없다.

**② 정의 파일에서 후보를 끊었다.** 거르는 것으로는 부족했다(앞 커밋은 스탯만 걸러 냈다) —
이제 아이템 이름 후보는 **이 챕터에 이미 있는 이름들뿐**이고, 대사 줄의 종류 판정도 정의
파일을 뒤지지 않는다. 새 이름은 그냥 적는다.

**③ 챕터 네임스페이스를 실제로 붙였다** (`Tier1Namespace`). Yarn의 변수 저장소는 하나라
(계약서 D1) 접두 없이는 1챕터의 `$열쇠`와 3챕터의 `$열쇠`가 **같은 변수**였다 — 저작은
챕터별인데 실행은 전역인, 정확히 "널브러진" 상태다.

- 접두는 **`__t1_{판Id}_`** — 뿌리가 판 Id라 **챕터 이름을 바꿔도 아이템이 초기화되지 않는다**
  (소유자 결정: 읽기 어려운 대신 개명에 안전한 쪽). Yarn을 직접 볼 일이 없다는 전제다
- **선언·set·조건식** 세 곳에 일관되게 적용한다. 하나라도 빠지면 선언과 사용이 어긋나 컴파일이 깨진다
- **A계층 스탯에는 붙이지 않는다** — 챕터를 넘어 사는 게 맞고 런타임 브리지가 이름 그대로
  왕복한다. 무엇이 스탯인지는 **추측하지 않는다**: 챕터 조건 공급 노드가 쓰는 이름만 스탯이다
- **합성 추적 변수(`$__ch_N`)도 그대로** — 노드 안에서 쓰고 버리는 값이다

**작업 중 실제 버그를 하나 잡았다.** 공급 노드 신원 판정이 `판 이름 == 챕터 Id`에 의존해서,
이름이 어긋난 프로젝트에서 **스탯 `trust`에 접두가 붙어 Yarn 컴파일이 깨졌다**(테스트가
잡았다). 이름 규약(`챕터 … 조건`)만으로도 알아보게 고쳤다 — 이 판정이 이제 내보내는 변수
이름을 정하므로 놓치면 게임이 깨진다.

**덤: 스탯 충돌 경고가 필요 없어졌다.** 작가가 아이템을 `trust`라 지어도 `$__t1_..._trust`가
되어 스탯을 건드리지 못한다 — 구멍 A가 **구조적으로** 닫혔다(§0.5가 예고한 그대로).
`WarnFreeNodeStatWrites`는 대사 줄 `<<set>>`에 대해서는 여전히 유효하다(그건 접두를 받으므로
실제로는 스탯을 안 건드리지만, 작가가 스탯을 바꾸려 했다는 의도 자체를 알려 주는 값이 있다).

골든 트리오·선언 파일을 새 출력으로 갱신했다(내용을 눈으로 확인 — 선언·set·조건이 모두 같은
이름으로 일치). 실제 Yarn 컴파일 테스트가 통과한다.

**테스트 1086 통과, 실패 0** (Ked 220 · Core 60 · Authoring 628 · App 178).

### 조건도 Set과 같은 감각으로 · 능력에는 부호가 없다 (소유자 지시, `(이 커밋)`)

**소유자** — "시나리오 그래프의 조건노드에서 조건을 만들 때에도, 대사노드에서 Set을 다루는
감각과 동일하게, 만든 아이템·능력을 고르고 `<=`, `=`, `>=` 부호를 고른 뒤 수치를 입력하도록
해줘. / 그리고 지금 능력은 On, Off인데도 부호가 있는데, 부호를 없애던지 혹은 `=`로
고정시키는게 좋겠어."

**① 조건이 세 칸이 됐다.** 예전에는 `게임이 평가할 식` 칸에 `$favor >= 5`를 **손으로**
적었다 — 작가가 Yarn 문법을 알아야 했고, 오타는 조용히 안 맞는 조건이 됐다. 이제
`[이름] [아이템·능력 ▾] [부호 ▾] [수치]`다. 챕터 `조건` 시트가 이미 같은 모양이라
(스탯·연산자·값) **두 계층의 조건 만들기가 같은 감각**이 됐다.

식 ↔ 세 칸 변환은 **챕터 시트와 같은 분해기 하나**를 쓴다(`ConditionExpressionParser`,
사본 금지) — 작가 식에는 `$`가 붙으므로 떼고 넣는다.

**② 능력에는 부호가 없다.** On/Off인데 `>=`·`+=`가 서 있었다.
- 조건: 능력을 고르면 **부호 칸이 사라지고** 값이 On/Off 토글이 된다 — 식은 `== true/false`
- 대사 줄 Set: 능력이면 **연산자 콤보를 감추고 `=`로 못 박는다**. 고를 것이 하나뿐이면
  고르게 하지 않는다

**손으로 적어 둔 복합식은 지킨다** — 여러 항을 묶은 식(`and`·`;`)은 분해하지 않고 읽기
전용으로 그대로 보여 준다. 조용히 뭉개면 원고가 사라진다.

고정 8개: 아이템 조건 다섯 부호가 각각 세 칸으로 나뉜다 · 능력 조건은 부호 자리에
true/false가 오고 값 칸은 비어 있다 · 복합식은 나누지 않는다.

**테스트 1094 통과, 실패 0** (Ked 220 · Core 60 · Authoring 636 · App 178).

### 능력 → 아이템으로 바꾸면 초기값이 `false`로 적히던 버그 (소유자 보고, `(이 커밋)`)

**소유자** — "능력에서 아이템으로 바꾸면 아이템의 초기값이 false로 적히는 문제가 있어."

**값 공간이 종류마다 다른데 안 쓰는 칸의 값이 그대로 넘어갔다.** 행에는 값 칸이 둘이다 —
능력이면 On/Off 토글, 아이템이면 숫자 칸 — 그리고 안 보이는 쪽도 살아 있다. 능력으로 보고
있던 행의 숫자 칸에는 `assignment.Value`가 그대로 들어 있었고(즉 `"false"`), 종류를 아이템으로
바꾸는 순간 그 문자열이 초기값으로 저장됐다.

**새 종류가 읽을 수 없는 값은 그 종류의 기본값으로 떨군다.** 아이템의 초기값은 숫자이므로
숫자로 못 읽으면 `0`에서 시작한다. 반대(아이템 → 능력)는 원래 On/Off 둘 중 하나로 떨어져
문제가 없었다.

고정: 능력(`false`) 행의 종류를 아이템으로 바꾸면 저장값이 `0`이다. **이 테스트가 고침 전에는
`Actual: "false"`로 실제로 실패하는 것을 확인했다** — 통과만 보고 넘기면 아무것도 안 지킨다.

**남은 이웃 사례(미착수)**: 대사 줄에서 이미 `= false`를 적어 둔 뒤 그 아이템의 종류를 바꾸면
줄에 남은 값은 낡은 채로 있다. 렌더에서 조용히 고치면 원고를 말없이 바꾸는 셈이라 손대지
않았다 — 실제로 걸리면 그때 규격을 정한다.

**테스트 1095 통과, 실패 0** (Ked 220 · Core 60 · Authoring 636 · App 179).

### 에피소드를 만들면 곧바로 쓸 수 있게 — 대본 자동 생성 + 빈 대본도 노드 (소유자 보고, `(이 커밋)`)

**소유자** — "챕터 그래프에서 ＋에피소드를 만들더라도 엑셀이 생성이 안돼. 그 에피소드 노드를
더블클릭 해야 엑셀이 생기는데, 그냥 처음부터 만드는게 맞을 것 같고. / 또 엑셀을 만들더라도,
시나리오 그래프에 반영되게 하려면 최소한 한 줄의 대사는 있어야해. 이게 진짜 엄청 헷갈려."

**두 증상의 뿌리가 각각 달랐다.**

**① 대본이 안 생기던 것 — 서로를 기다리는 매듭.** 툴의 [＋ 에피소드] 버튼은 원래도 대본을
만들고 있었다(테스트로 확인). 빠진 것은 **엑셀에서 직접 행을 더한 경우**인데, 그게 기본
작업 방식이라 대부분이 그 길이다. 그리고 그 길은 두 겹으로 막혀 있었다:

- `SyncEpisodes`가 `if (!Directory.Exists(folder)) return;`으로 멈췄다
- 더 위에서, `WatchAndReload`가 **감시자가 못 붙으면 동기화까지 건너뛰었다**
  (`episodesFolderChanged && _episodeWatcher is not null`)

**폴더는 대본이 생겨야 나고, 대본은 동기화가 만드는데, 그 동기화가 폴더를 기다렸다.**
그래서 첫 에피소드는 영영 대본을 못 받고, 노드를 더블클릭해야(그 경로가 따로 만든다) 생겼다.
이제 동기화가 **모든 에피소드에 대본을 보장**하고, 첫 대본이 폴더를 만들며, 그 김에 감시도
붙는다. 없는 파일을 만드는 것뿐이라 단일 writer 원칙과 충돌하지 않는다(있으면 무접촉).

**② 빈 대본이면 노드가 안 서던 것.** `EpisodeSyncService`가 **노드를 만들기 전에** 되돌아갔다
— "아직 쓸 게 없다"는 판단은 옳았지만 그 자리가 틀렸다. 기획자가 에피소드를 만들어도 작가의
판에는 아무것도 없었고, 작가는 무엇을 기다려야 하는지 알 수 없었다("진짜 엄청 헷갈려").

노드 생성을 앞으로 당기고 **본문만 건드리지 않는다**(빈 글을 밀어 넣으면 지우기로 읽힌다).
빈 노드라도 서 있으면 "여기에 쓰면 된다"가 보인다. 여전히 `NotYetWritten`이라 배지에는 안
센다 — 아직 안 쓴 것은 잘못이 아니다.

**`StatChangeEditor` — `[스탯 ▾][＋/－][수치][✕]` + [＋ 스탯변화].** 대사노드의 Set 편집기와
같은 감각이다: 사람은 고르고 누르지 문법을 외우지 않는다. 드롭다운은 엑셀 `스탯` 시트에
선언된 것만 담고, bool 스탯은 부호 대신 **켬/끔**에 수치칸이 없다(`+5`가 남으면 값 공간
0·1을 벗어난다 — 종류를 바꿀 때 수치를 물려받지 않는 것도 같은 이유).

**자리는 둘, 값의 주인은 하나.** 간선 패널의 자유 입력 칸을 이 편집기로 갈고, **에피소드
노드의 선택지 폼**에도 같은 편집기를 하나 더 놓았다 — 소유자가 노드에서 바로 만지고 싶어
한 자리다. 새 저장소는 없다: 둘 다 `간선` 시트의 `스탯변화` 칸 하나에 쓴다. 그래서 폼의
[잇기]/[수정]은 **배선과 증감을 한 저장으로** 낸다(`AddEdge`·`SetEdgeRoute`가 `statChanges`를
받는다) — 두 번 쓰면 그 사이에 엑셀이 파일을 잡아 반쪽만 적힌 길이 남는다.

**테스트가 내 버그 둘을 먼저 잡았다.** 처음엔 줄을 목록의 <b>번호</b>로 잡았는데, 다시
그릴 때마다 그 번호가 낡아 ① 사람이 친 수치가 조용히 사라지고 ② 줄을 지우면 없는 자리를
짚어 터졌다. 지금은 줄 하나가 물건 하나이고 사건 처리기가 그 물건을 잡는다 — 빠진 줄의
처리기가 뒤늦게 울어도 고아를 고칠 뿐이다. 수치는 낼 때 컨트롤에서 읽는다(사건 순서에
기대지 않는다).

**빈 챕터에서도 보이게.** 아무 스탯도 안 움직이는 챕터에서는 거르지 않고 초기값을 보여
준다 — 거를 것이 없을 때 빈 카드는 "기능이 없다"로 읽힌다. 증감을 하나라도 적는 순간
움직이는 스탯만 남는다.

**다시 읽기**는 남긴다. `ChapterFolderWatcher`가 챕터·에피소드 폴더를 감시하니 평소엔

옳았던" 판이다).

잡았다 — 다시 읽기 뒤에 동기화 보고가 따라와 `"에피소드 0개를 반영했습니다"`가 덮어
버렸다. 못 나간 사유는 어차피 그 보고에 이미 서 있는 오류들이라, **결론을 근거 옆에**
둔다: 보고 맨 위 붉은 줄 + 머리글 `· 진행 JSON 미출력`(접혀 있어도 보인다) + 자동 펼침.
잘 나갔을 때는 아무 말도 없다 — 파일이 있다는 것이 증거다.

에피소드는 그 결과의 도달 집합에 없으니 전부 "도달 불가"로 붉게 서고, 도착 스탯 폭도 같은
결과에서 오므로 빈칸이었다. Ctrl+S는 세션 `Changed`를 울려 `WatchAndReload`를 부르고, 그
경로가 `Validate()`를 돌려 주니 "그제서야" 맞았던 것이다. 그리고 드롭다운은 판을 활성으로
바꾸지 않으니 왼쪽 목록의 강조(활성 판을 본다)도 따라오지 않았다.

**길을 하나로 합쳤다.** 드롭다운도 `SelectChapter`를 지난다. 그 안에 검증 재실행 ·
이전 챕터의 선택 비우기(없는 간선을 가리키지 않게) · `ChapterSelected` 알림이 모여 있고,
셸이 그 알림을 듣고 판을 옮기며 목록을 다시 그린다. 판을 만드는 일은 셸의 몫이라
(`EnsureChapterBoard`) 뷰가 직접 하지 않는다 — 이 뷰는 프로젝트를 안 고친다.

### 대본 v10 — 조건 분기가 블록이 된다 (소유자 결정, `(이 커밋)`)

**소유자** — "대본 엑셀에서 유형과 태그, In, Out이 고민이야." 넷의 처지를 세어 보니 이미
기울어 있었다: `유형`의 CHOICE·OPTION은 v9에서 죽었고(선택지의 주인이 챕터 시트로 갔다),
`태그`·`IN`·`OUT` 셋은 **한 개념(조건 분기)을 네 열·세 행에 흩어** 놓고 있었으며,
`OUT`은 흐름을 바꾸는 힘이 없는 선언이라 맞으면 아무 일도 없고 틀리면 오류만 냈다.
게다가 그 모델은 **중첩을 금지**했다.

**소유자 선택: IF 블록.** `IF`행 ~ `ENDIF`행이 그 사이를 감싼다. 열이 9 → **6**으로 줄고
(`인덱스·LineId·유형·조건라벨·화자·내용`), §3.3의 규칙 1·2·4·5·6이 **짝 하나**로 줄었다.

**평평화는 한 번 훑기가 됐다.** 예전에는 구간을 그 자리로 <b>옮겨</b> 넣었고 "각 행은 정확히
한 번 나온다"를 규칙 넷으로 지켜야 했다. 블록에서는 행이 이미 제자리에 있으므로 그 성질이
**걷기에서 저절로 나온다** — LineId 전역 유일성(계약서 C1)도 거기서 온다.

**이행기가 구간을 제자리로 옮긴다**(`.bak`). **인덱스는 절대 다시 매기지 않는다** — 그
번호가 줄의 신원이고 `ExcelLineMap`이 그것으로 LineId를 붙들고 있다. 다시 매기면 그 줄에
달아 둔 연출이 통째로 끊긴다. 그래서 옮긴 뒤 번호가 뒤죽박죽이 되는데, **오름차순을 권고로
내린 것**이 정확히 이 때문이다(읽는 순서는 행 순서다).

#### 중간에 벽을 만났다 — 그리고 아래층을 고쳤다

중첩을 넣고 보니 **작가 판이 못 받았다.** 줄 하나가 전환 <b>하나</b>만 담았고(슬롯 하나),
합성기의 조건 깊이는 0·1뿐이었다. Yarn에는 전환만 있는 줄이 없어서 겹쳐 닫는 `<<endif>>`
둘이 같은 줄 앞에 몰리는데, 그걸 표현할 그릇이 없었다. **인접한 블록 둘도 같은 이유로
못 썼다.** 구판이 중첩을 금지한 진짜 이유가 "엑셀의 경계가 모호해서"가 아니라 여기였다.

소유자에게 물었고 답이 명확했다 — **"조건 블록은 시나리오 그래프에서 갈래로 보일 필요 없이,
대본이 정한 대로 흘러가면 된다."** 그 한마디로 흐름 계산기·노드 편집기·갈래 그리기가 통째로
범위에서 빠졌다. 남은 것은 **통과 화물**이다: 줄이 구조 토큰을 순서대로 들고 가고, 합성기가
깊이 카운터로 되뱉는다. 작가 판은 그게 무슨 조건인지 모른다.

- `DialogueLineExtension.Transitions` 목록 (+ 첫 칸을 주는 `Transition` 호환 이름)
- 프로젝트 JSON: 전환이 하나면 예전 `condition` 한 칸 그대로, 둘 이상만 `conditions` 배열
- 편집기: 한 줄의 전환은 **묶음**이다 — 하나를 못 세우면 나머지도 반영하지 않는다
- 합성기: `conditionOpen` 불리언 → 깊이 카운터. 표지는 바깥 깊이, 본문은 안쪽 깊이

**곁다리로 진짜 구멍 하나를 막았다** (소유자 보고 — "`<<endif>>` 뒤따르는 대사 줄이 없어
붙일 곳이 없습니다"). 조건 블록이 에피소드의 마지막이면 닫힘을 실어 나를 줄이 없다. 선택
블록에는 "문서 끝까지 열려 있으면 닫는다"가 있었는데 **조건 쪽에는 없었다** — 그대로 두면
`<<if>>`만 있는 Yarn이 나가 컴파일이 깨진다.

**`ELSEIF`도 넣었고**(`유형` 넷째 낱말), **`대사`를 목록에 세웠다**(소유자: "IF와 END밖에
못 골라" — 셀을 지우는 대신 고를 수 있어야 한다). **`ENDIF`가 정본**이다: `END` 혼자면
"에피소드가 여기서 끝난다"로 읽힌다(구판 `OUT` 열의 `END`가 정확히 그 뜻이었다).

**`유형` 드롭다운이 옛 파일에도 온다.** 화자·조건라벨은 숨김 시트를 갈아 끼우면 따라오는데
이 목록은 **낱말이 파일에 굳어서** 만들 때 한 번 박히고 끝이었다(소유자: "유형이 여전히
IF와 END밖에 없어"). 이제 동기화마다 대조해 다르면 다시 건다.

**조건라벨(D)도 드롭다운이 됐다** — 챕터 `조건` 시트에서 온다. 오타가 곧 오류인 칸이라
화자보다 값이 크다. 화자와 **한 번의 쓰기**로 넣는다(따로 저장하면 `.bak`이 두 번 덮여
되돌릴 자리가 없어진다).

**테스트 1140 통과, 실패 0** (Ked 220 · Core 60 · Authoring 641 · App 219).
견본 워크북의 대본 시트도 v10 실물로 다시 깔았다 — 중첩과 `ELSEIF`를 한 판에 담는다.

### 대사 미리보기가 ELSEIF를 몰랐다 (소유자 보고, `(이 커밋)`)

**소유자** — "편집탭에서 대사를 아래로 펼쳤을 때, IF 처음껀 잘 반영되는데 elseIf는 반영이
안되네."

미리보기가 유형을 `IF` / `ENDIF` / 그 외로만 갈랐다. `ELSEIF`는 "그 외"로 떨어져 화자·내용을
읽으러 갔는데 그 칸이 비어 있어 **빈 줄로 걸러졌다** — 데이터는 멀쩡한데 화면에서만 사라졌다.

이제 셋을 각자 센다. 표지는 평평화의 `<<elseif>>`와 <b>같은 자리</b>에 선다 — 같은 체인의
바깥 깊이이고 깊이는 변하지 않는다. 그래서 시트를 읽는 눈과 산출 Yarn의 모양이 일치한다.

고정 하나. 견본이 중첩과 `ELSEIF`를 한 판에 담으므로, 미리보기 전체를 한 줄씩 대조하는
검사로 바꿨다 — 세 겹이 전부 걸린다. 고치기 전 실제로 실패하는 것을 확인했다.

풀려버려서 글자를 쓸 수가 없네. / 표정 역시 이미 있다고 그대로 쓰라고 하는 대신 덮어쓸
수 있도록 해줘."

#### ① 글자 하나마다 칸이 교체됐다

`SetWriterSpeakers`가 변경을 `Structure`로 알리고 있었다. 셸은 그 신호에 그래프와
**편집기를 통째로 다시 만든다** — 글자 하나 칠 때마다 쓰던 TextBox가 새것으로 갈리니
초점이 날아갔다. 선이 움찔한 것도 같은 신호가 부른 그래프 재구성이었다.

**화자 목록은 구조가 아니다.** 노드도 간선도 아니고 드롭다운의 재료일 뿐이라 `Content`가
맞다(판도 편집기도 안 건드리고 대사 미리보기만 새로 읽는다). `ProjectRefreshPlanner`의
클래스 주석이 이 회귀를 미리 적어 두고 있었다 — "LostFocus 커밋이 컨트롤을 교체해서 두
번째 칸을 클릭할 수 없게 했다". 같은 함정을 다른 목록에서 다시 밟았다.

**앞선 고정이 이걸 못 잡은 이유**도 분명하다: 모델만 보고 화면을 안 봤다. 이번에는 같은
TextBox 인스턴스가 그대로 서 있는지(`Assert.Same`)와 `Structure`로 알리지 않는지를 건다.

#### ② 표정은 덮어쓸 수 있다

이미 있으면 단추가 잠기고 "이미 있는 표정입니다"로 끝이었다 — 그림을 고쳐 다시 넣으려면
탐색기로 파일을 지우고 돌아와야 했다. 이제 단추가 **"이미지 선택해 덮어쓰기…"**가 되고
그 자리를 바꾼다.

조용히 덮지는 않는다: 부르는 쪽이 `overwrite: true`를 적어야 하고(기본은 예전처럼 거부),
지워지는 그림은 같은 폴더에 `.bak`으로 남는다. `.bak`은 `.png`가 아니라 에셋 목록에
잡히지 않는다. 잘못 고른 파일 하나로 쓰던 초상화가 사라지면 되돌릴 길이 없다.

고정 4개: 치는 동안 칸이 안 바뀐다(고치기 전 실패 확인) · 덮어쓰면 바뀌고 직전은 `.bak` ·
없던 자리는 덮어쓴 것이 아니다 · 기본은 여전히 거부.

### 작업 순서가 곧 탭 순서 — 연출 그래프 개명·휠 확대·자료 우측 이사 (팀장 미팅, `(이 커밋)`)

어제 팀장에게 작업물을 넘겼고, 그 자리에서 나온 것을 소유자가 정리해 왔다.
바탕에 깔린 판단 하나가 나머지를 전부 설명한다 — **기획자가 사실상 시나리오 작가다.**

> **소유자** — "기획자가 사실상 시나리오 작가이다보니, 사실 대부분의 스토리는
> 챕터그래프에서만 작성해도 충분할 것 같아. 따라서 시나리오 그래프의 이름을
> 연출그래프로 바꾸고, 시나리오 그래프의 기능은 더 늘리지 않는게 맞다고 판단했어."

#### ① "시나리오 그래프" → "연출 그래프", 그리고 챕터 그래프가 첫 탭

이름이 일을 오해하게 하고 있었다. 스토리가 챕터 그래프에서 끝난다면 저 판에 남는 일은
연출뿐인데, "시나리오 그래프"라는 이름은 거기서 시나리오를 또 쓰라고 부른다. 이름을
일에 맞추고 **기능 동결**을 함께 적었다 — 이 판은 여기까지다.

탭 순서도 뒤집었다(소유자: "왼쪽에서 오른쪽으로 하나씩 작업하면 완성할 수 있도록").
`챕터 그래프 → 연출 그래프`. 탭 줄이 곧 작업 순서를 가르친다.

순서를 뒤집자 **시작 화면만 어긋나는 구멍**이 하나 열렸다. 우측 열을 접는 계산이
`SelectionChanged` 안에만 있었는데, 그 이벤트는 **이미 정해진 첫 선택에는 오지 않는다** —
전에는 첫 탭이 연출 쪽(=펼침, XAML 기본값)이라 우연히 맞았을 뿐이다. 계산을
`ApplyTabChrome()` 하나로 꺼내 생성자와 탭 전환이 **같은 것**을 부르게 했다. 시작 화면만
따로 세우면 두 벌이 되고, 두 벌은 반드시 어긋난다.

#### ② 휠만으로 확대·축소 — Ctrl 요구 해제

> **소유자** — "현재는 ctrl+휠이 확대 축소인데, 그냥 휠만으로 확대축소가 가능해야하고"

두 판(`ChapterGraphView`·`GraphEditorView`)에서 Ctrl 검사를 지웠다. 판 위에서 휠은 곧
배율이고, 세로로 훑는 일은 가운데 단추 끌기가 맡는다. **Ctrl+휠도 그대로 배율이다** —
손에 익은 사람이 그대로 써도 같은 결과여야 한다. 화면의 안내문·툴팁도 함께 고쳤다
(그 문구가 "Ctrl+휠"이라고 적힌 채 남으면 툴이 거짓말을 한다).

#### ③ 편집 자료·에셋 = 왼쪽 → 우측 맨 아래, 접힌 채로

> **소유자** — "챕터목록은 좌측이 맞는데, 편집자료와 에셋은 우측으로 빼버려서 시각적
> 주목도를 크게 낮추는게 맞다고 판단이 들어. 정확히는 평소에 굳이 보일필요가 없지."

왼쪽 열이 `챕터 목록(2*) + 편집 자료(3*) + 에셋(300px)`이었다 — **챕터 목록이 왼쪽의
3분의 1도 못 쓰고 있었고**, 늘 펼쳐진 현황판 둘이 그보다 큰 자리를 먹었다. 왼쪽은
챕터 목록 하나가 됐고(`Auto,*`), 둘은 우측 열 맨 아래로 내려가 **접힌 채로** 선다.
에셋 탐색기는 제 머리에 접기 토글을 이미 갖고 있어 기본값만 뒤집었고, 편집 자료에는
같은 문법(▶/▼)을 새로 달았다 — 판이 둘인데 접는 법이 다르면 손이 매번 헷갈린다.

**따라오는 결과 하나**: 우측 열은 챕터 그래프 탭에서 통째로 접히므로, 그 탭에서는
편집 자료·에셋에 닿을 길이 없다. 둘 다 연출 계층의 자료라 연출 그래프 탭에 사는 것이
맞다고 보고 그대로 뒀다 — 챕터 탭에서도 닿아야 한다면 별도 규격이 필요하다(열린 항목).

#### 하지 않은 것 — 우클릭

메모의 `(4) 우클릭 기능 추가`는 소유자가 **보류**했다("필요하긴 하지만 아직도 추가는
하지 않을거야"). 기록만 남긴다.

#### 되돌리는 법

탭 순서·이름은 `MainWindow.axaml`의 `TabControl` 두 `TabItem`을 도로 바꾸면 된다
(`ApplyTabChrome()`의 생성자 호출은 남겨 두는 편이 안전하다 — 순서와 무관하게 옳다).
휠은 두 `OnGraphWheel`에 `KeyModifiers.Control` 검사를 되돌리면 되고, 자료 이사는
`MainWindow.axaml`의 좌·우 열 두 덩이를 맞바꾸면 된다.
