# 확정된 설계와 그 이유

**이 문서는 요약이다.** 규범적 원문은 `../../ARCHITECTURE.md`(구조)와 `../vntool-master-plan.md`(제품),
`../runtime-contract.md`(런타임 계약)에 있고, 충돌하면 그쪽이 우선한다.
여기서는 **"왜 이렇게 됐는지"**를 남긴다 — 이유를 모르면 다음 세션이 되돌리기 때문이다.

---

## A. 도메인 모델

### A-1. 진실은 순수 텍스트, 원본은 셋으로 나뉜다
`ScriptDocument`(화자·대사) / `StoryNode`(논리·연출) / `Result`(얼어붙은 발행)가 겹치지 않는다.
**이유**: 형식 버전 2에서 `LineBox`가 본문의 수정 가능한 복사본을 들고 있었고, 그래서 "어느 쪽이 진실인가"에 답할 수 없었다.

### A-2. LineId는 영구 불변이다 (최상위 불변식)
세이브 시킹(계약서 C1)·연출 바인딩·CSV·녹음·번역이 전부 여기 걸려 있다.
재파싱은 **언제나 diff 기반**이고, 확신할 수 없으면(`Ambiguous`) **전량 거부**한다.
**이유**: 임의로 이으면 작가가 쓰지 않은 연출이 다른 대사에 붙고, 그 사실은 최종 출력에서야 드러난다.

### A-3. 대사노드 = CompositionNode (D-1), 발행은 연출 바인딩용 스냅샷 (D-2)
편집 즉시 현재 상태가 합성되어 출력 폴더에 저장된다. 발행은 출력 게이트가 **아니고**, 연출노드가 읽을 읽기전용 스냅샷만 만든다.
**단, 연출↔대사 버전 짝 추적은 유지된다** — 연출이 읽은 발행본과 현재 대사가 다르면 경고(차단 아님).
**이유**: 출력을 보려고 매번 발행을 눌러야 하는 게이트가 실사용에서 마찰이었다. 조용한 드리프트는 여전히 금지라 경고만 남겼다.

### A-4. 대본 가져오기 제거 (D-3)
진입점은 대사노드 직접 편집 + ScenarioOnly 붙여넣기 둘뿐이다.
**이유**: 두 입력 트랙이 같은 diff 엔진을 다르게 부르면 규칙이 둘이 된다.

### A-5. Speaker 원천 = `game.definition.json` (D-4)
설정노드의 등록 UI는 **편집 창구일 뿐 사본을 갖지 않는다.**
**이유**: 원천이 둘이면 파일을 손으로 고친 날 양쪽이 오류 없이 어긋난다.

## B. 규칙 사본 금지 — 같은 규칙은 코드에 한 곳만

| 규칙 | 유일한 자리 |
|---|---|
| Yarn 표기 조립 | `YarnSyntax` (Preview·이미터·ScenarioOnly가 공유) |
| 커맨드 텍스트 ↔ 구조 | `CommandText` (병기 텍스트·직접 입력 파싱·이미터 인자 순서) |
| 초상화 경로 ↔ 키 | `PortraitKey.ToRelativePath` / `TryParseRelativePath` |
| 라인 diff | `ScriptSynchronizer` (붙여넣기가 그대로 재사용) |
| 공급 짝 계산 | `NodeExportResolver` |
| 합성·출력 | `LiveNodeComposer` → `YarnBundleEmitter` (라이브·수동·노드 단위 전부) |
| 번들 이름(= 파일명·Yarn 타이틀·세이브 키 C2) | `YarnBundleEmitter.BundleNameOf` (이미터·점프 대상·고아 판정) |
| 모델 변경 | `ProjectEditor` (직접 조작·드래그·텍스트·갤러리 전부 수렴 — ARCHITECTURE 규칙 15) |
| 무대 렌더 | `StageSceneView` (도킹 패널·분리 창 공용) |

**이유**(원칙 §2.4): 런타임과 툴이 같은 규약을 각자 구현하면, 규약이 바뀌는 날 **양쪽 다 오류 없이 어긋난다.**

## C. 침묵을 만들지 않는다

### C-1. 조용히 버리지 않는다 (ARCHITECTURE 규칙 14)
폴드가 못 그리는 커맨드는 `Unhandled`(커맨드명+라인 보존)로, 못 찾은 에셋 키는 키 문자열이 보이는 플레이스홀더로,
붙여넣기가 해석 못 한 줄은 목록으로 화면에 남는다.
**이유**: 이 코드베이스의 실패는 대부분 예외가 아니라 침묵이었다(원칙 §2.5). 보이면 확장이 한 커맨드씩 늘어나는 작업이 되고, 안 보이면 "왜 이 장면만 다르지"로 돌아온다.

### C-2. 편집기 예외 전부 포획 (ARCHITECTURE 규칙 4, X1)
UI 핸들러의 예외가 디스패처를 지나면 프로세스가 죽는다. `UiGuard`로 포획해 **무동작 + 상태줄 사유**로 바꾸고,
`Dispatcher.UIThread.UnhandledException`이 마지막 안전망이다.
**이유**: 클릭 하나가 앱과 미저장 원고를 같이 끝내서는 안 된다.

### C-3. 낡은 출력은 보여 주되 지우지 않는다 (K1 ②안, 소유자 확정 2026-08-04)
노드를 지우거나 이름을 바꾸면 옛 `.yarn`이 출력 폴더에 남는다. VnTool은 그것을 **고아 출력**으로
상태줄과 [양식…] 목록에 올리고, **파일은 건드리지 않는다.** 판정 기록은 출력 폴더의 `.vntool-output.json`이고,
기록에 없는 파일은 이름 형식이 같을 때만 "(기록 없음)"으로 구분해 올린다.
**이유**: 출력 폴더는 사용자의 폴더이지 도구의 소유물이 아니다. 폴더를 잘못 지정한 사람이
자동 회수로 자기 파일을 잃는 쪽이, 낡은 파일을 손으로 지우는 쪽보다 훨씬 나쁘다.
**같이 검토하고 미룬 것 — 번들 이름을 노드 Id로(③안)**: 이름 변경 시 파일 증식은 막지만,
번들 이름은 파일명이자 **Yarn 타이틀 = 세이브 키 = 에피소드 진입 키(계약서 C2)이고 모든 점프 대상**이다
(`YarnBundleEmitter.BundleNameOf` 한 곳). 바꾸면 세이브 호환과 유니티 쪽 가독성이 함께 걸리고,
**삭제 문제는 여전히 남는다.** 하려면 세이브가 실제로 생기기 전에 별도 결정으로 한다.

### C-4. 추측 보정 금지 (원칙 §2.3)
텍스트 입력의 오타는 "비슷한 이름"으로 고쳐 주지 않고 그 자리에서 오류로 말한다. 에셋도 유사 이름 매칭이 없다.
**이유**: 규칙이 "이름이 같으면 연결된다"에서 "툴이 알아서 해준다"로 바뀌는 순간, 툴이 없는 자리에서 사람이 뭘 해야 할지 모르게 된다.

## D. 에셋 — 연결의 권위는 폴더 규약 (W-asset-02)

> 런타임과 툴이 공유하는 것은 **키 공간**(`PortraitKey`)이지 저장 방식이 아니다.

런타임은 키를 DBSO에, 툴은 폴더 구조(`{char}/{variant}/{emotion}.png`)에 담는다. 매니페스트는 자유 경로 수입 보조일 뿐이다.
배경은 파일명(하위 폴더 포함)이 곧 키.
**이유**: 비전공자가 "파일을 이름 맞춰 넣으면 된다"고 믿게 하려면 그 믿음이 참이어야 한다. 매니페스트가 권위면 툴 없이는 에셋을 못 넣는다.

## E. 계산은 저장하지 않는다

`MiniStageFold`·`StatFold`·`StageSceneComposer`·`AssetExplorerModel`·`ConditionFlowResolver`는 전부 순수 함수이고 결과를 모델에 쓰지 않는다.
그래프 포트·간선도 저장이 아니라 계산이다.
**이유**: 저장하면 원본과 파생이 어긋날 자리가 생기고, 어느 쪽이 맞는지 물어야 한다.

## F. 근사는 근사라고 화면에 쓴다

v1 폴드는 갈래를 가리지 않고 문서 순서로 전부 적용한다(스탯 HUD도 같다). 그 사실을 UI가 숨기지 않는다.
대사창의 `Portrait`/`Surface`/`BlackBook`은 Speaker 근사로 그리고 "(근사)" 뱃지를 단다.
**이유**: 정확한 갈래 시뮬은 2b의 일이다. 근사를 정확한 척하면 그 화면을 믿고 틀린 판단을 하게 된다.

## G. 형식·호환

- **형식 버전 2 이하는 열지 않는다**(마이그레이션 대신 거부). 자동 해석하면 어느 문장이 어느 LineId인지 도구가 임의로 정하게 된다.
- 새 필드는 **기본값 생략 직렬화** → 기존 프로젝트 파일 바이트 불변. `assetRoots`·`recentCommands`·`exportFormats`·`outputPath`·변수 `type`/슬라이더 범위가 전부 이 방식이다.
- 되돌리기는 `ProjectSnapshotCodec`의 aggregate 문자열 — 디스크 배치와 독립.

## H-2. 무대 상태 계산은 런타임 코어 **한 벌** (Phase 2b, D-2b-1 확정 2026-08-05)

`Ked.Presentation.Core`(런타임 U13)의 리듀서를 **VnTool이 참조해서 같이 쓴다.**
VnTool이 커맨드 해석을 따로 구현하지 않는다 — `MiniStageFold`는 코어 도착 시 교체된다.

**이유**: 런타임 연출은 전부 UI로 재생되고 **좌표가 전부 RigSpaceRoot 픽셀 기준**이다
(`runtime-contract.md` §104). VnTool도 기준 해상도 캔버스에 그리므로 **두 좌표계는 원래 같다.**
상태 계산 층에는 유니티 의존이 없고(셰이더는 마지막 그리기에서만, 그것도 커맨드 201개 중 37개의
시각 효과 부분에만), 그러면 같은 규약을 두 번 구현할 기술적 이유가 남지 않는다 — 두 벌이면
규약이 바뀌는 날 양쪽 다 오류 없이 어긋난다(원칙 §2.4, §B와 같은 실패 모양).

**딸린 제약**: 코어는 `UnityEngine` 타입(`Vector2`·`Rect`·`Color`·`RectTransform`)에 의존하지 않고
자체 값 타입을 쓴다. **이 제약은 U13 지시서에 실려야 한다** — 지시가 나간 뒤 요구하면 재작업이다.
**행동의 진실은 런타임이 갖는다**(실제로 재생하는 쪽) — 리듀서 본문은 런타임에서 나오고,
VnTool의 층 구조(폴드 → 배치 → 그리기)와 "조용히 버리지 않는다"는 코어 요구사항으로 올린다.

**폐기한 대안**: ② 각자 구현 + 교차 검증(전제가 무너졌다), ③ 런타임이 상태를 덤프하고 툴은
그리기만(공유가 가능한데도 유니티를 켜야 프리뷰가 도는 쪽 — 2a-v1의 성과를 잃는 후퇴).

## H-3. 2b의 "구도 일치"는 축마다 등급이 다르다 (D-2b-2 확정 2026-08-05)

| 축 | 등급 |
|---|---|
| 슬롯 배치·뎁스·샷·대사창 | **재현** — 픽셀 산수 + 공유 좌표계라 근사할 이유가 없다 |
| dim·실루엣·플래시·비네트 | **근사(표시)** — 알파·단색·오버레이로 뜻은 전달된다 |
| 블러·림 라이트·노이즈·마스크 모션 | **미표시(뱃지)** — 상태는 갖되 그리지 않고, 안 그렸다고 화면에 쓴다 |

**이유**: 근사끼리 눈대중으로 맞추는 수용 기준은 판정이 불가능하다. 재현 가능한 축을 먼저
재현으로 못박아야 "구도 일치"가 검증할 수 있는 목표가 된다. 근사·미표시는 규칙 14대로 화면에 남는다.

## H-4. 코어 참조 방식 = 관리된 소스 수입 (submodule 반려, 확정 2026-08-05)

VnTool은 `Ked.Presentation.Core`를 **동기화 스크립트가 만든 소스 수입본 + 콘텐츠 해시 잠금**으로 참조한다.

- 동기화는 한 방향(런타임 → 툴)이고 스크립트만 한다. **수입본 편집 금지** — 코어를 고칠 일이
  생기면 런타임 저장소 지시로 돌린다(H-2 "리듀서 본문은 런타임에서 나온다"와 같은 자리).
- `core-source.lock.json`이 원본 커밋·동기화 시각·콘텐츠 해시를 기록하고, **테스트가 수입본의
  실제 해시를 lock과 대조한다** — 수입본을 손으로 고치거나 절반만 갱신하면 시끄럽게 실패한다.
- 코어의 순수 테스트(UnityParity 제외)도 함께 수입해 툴 쪽 러너로 돌린다 — 수입본이
  "빌드만 되는 소스"가 아니라 "검증까지 통과한 소스"가 된다.

**이유**: 문서가 추천했던 (가) submodule은 소유자가 반려했다(2026-08-05). 코어가 유니티 저장소
*안*(`Assets/Ked.Presentation.Core/`)에 살아서 submodule은 유니티 프로젝트 전체를 툴 저장소에
끌고 들어오고, VnTool 작업물은 zip 스냅샷으로도 이동하므로 이웃 체크아웃 상대 경로 참조는
자립 빌드를 깨뜨린다. NuGet은 코어가 U14 수렴으로 아직 자주 움직이는 지금 단계에 패키징 마찰이 크다.

**사본 금지(§B)와의 관계**: §B가 금지하는 것은 *따로 진화하는 재구현*이다. 이 수입본은
갱신이 기계적이고 편집이 해시로 감시되는 **배포 채널**이라, §B가 막으려는 실패 모양
("규약이 바뀌는 날 양쪽 다 오류 없이 어긋난다")이 침묵할 방법이 없다 — submodule이
커밋 핀으로 하던 "어느 커밋의 코어인지 명시"는 lock의 `runtimeCommit`이 한다.

## H. 게임별 어휘는 전부 데이터

변수·이벤트·조건·커맨드 카탈로그·카테고리·화자 매핑·프리뷰 해상도가 전부 `game.definition.json`에서 온다.
코드가 `favor`나 `bg_spawn`을 아는 순간 그 게임 전용 도구가 된다.
