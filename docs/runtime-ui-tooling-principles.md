# 런타임 UI 구조에서 얻은 툴 설계 원칙

작성 2026-08-03. `ked-presentation-runtime`의 UI 테마 패치 시스템을 읽고 도출.
대상: VnTool(`java-start`) 제작 세션.

이 문서는 **원칙과 근거**다. 작업 지시가 아니다.
런타임 저장소를 고치라는 내용은 여기 없다 — 그쪽은 별도 사양서(`ui-sprite-port-board-spec.md`)가 있다.

---

## 0. 요약

런타임의 UI 테마 패치는 규모가 작은데도 **툴 만들기 좋은 구조**의 조건을 거의 다 갖추고 있다.
그 조건이 무엇인지 분해하면, VnTool의 에셋·연출 편집기에 그대로 옮길 수 있는 원칙이 나온다.

핵심은 하나다.

> 툴이 편한 이유는 툴이 똑똑해서가 아니라, **규칙이 전함수여서** 툴이 답을 *계산*할 수 있기 때문이다.

---

## 1. 왜 이 시스템은 툴 만들기 좋은가

### 1.1 주소가 전함수다

```csharp
// SpritePortAssignmentBuilder.cs
return $"ui/{context.ThemeId}/{portId}";
```

`(테마, 포트) → 주소`가 조건 분기 없는 순수 함수다.
그래서 **기대되는 에셋 전체 집합을 툴이 정확히 계산할 수 있다.** 탐색이 아니라 계산이다.

이게 없으면 툴은 "무엇이 있어야 하는가"를 알 수 없고, 있는 것만 보여주는 파일 브라우저가 된다.

### 1.2 대상 집합이 타입에서 정적으로 유도된다

```csharp
// UIBase.SpritePorts.cs — Refs(Enum)를 스캔해 "_Image"로 끝나는 것을 포트로 인식
foreach (TRefs enumValue in Enum.GetValues(typeof(TRefs)))
    if (enumValue.ToString().EndsWith("_Image", StringComparison.Ordinal))
        _cachedSpritePortIds.Add(name);
```

포트 목록이 **씬을 열지 않고, 게임을 실행하지 않고, 직렬화 데이터 없이** 타입만으로 나온다.
에디터 툴이 리플렉션만으로 완전한 목록을 얻는다.

> **VnTool 적용**: 커맨드 카탈로그도 같은 성질을 갖는다.
> `game.definition.json`이 어휘를 공급하므로 "무엇이 있어야 하는가"가 데이터로 계산된다.
> 이 성질을 잃는 설계(예: 커맨드를 코드에 하드코딩)는 툴을 즉시 어렵게 만든다.

### 1.3 두 성질이 함께여야 한다

전함수만 있고 대상 집합을 모르면 → 무엇을 계산할지 모른다.
대상 집합만 있고 주소가 조건부면 → 계산 결과가 여러 갈래다.

**툴을 염두에 둔 설계란, 이 두 성질을 지키는 설계다.**

## 2. 툴 설계 원칙 다섯

### 2.1 착각을 지키는 것이 설계 제약이다

비전공자가 "이름만 맞추면 자동으로 연결되는구나"라고 착각하고 편하게 쓰게 하는 게 목표라면,
**그 착각은 참이어야 한다.**

> 목록에 뜨는 칸은, 채우면 반드시 동작한다.

채워도 동작하지 않는 칸이 하나라도 있으면 사용자는 다음부터 목록을 믿지 않는다.
그리고 신뢰는 한 번 깨지면 "그럼 뭘 믿어야 하지"로 번진다.

**따라서 예외가 발견되면 예외 표시 장치를 만들지 말고 예외 자체를 없앤다.**
런타임에서 실제로 그랬다 — 코드가 직접 대입하는 포트 3개가 규약과 경합하고 있었는데,
속성이나 예외 목록으로 표시하는 대신 파일을 규약 위치로 옮기고 대입 코드를 지우는 쪽을 택했다.
예외가 0이 되면 표시 장치도 필요 없다.

### 2.2 툴 없이도 되어야 한다

툴은 **편의**이지 **통로**가 아니다.

UI 스프라이트 교체는 두 경로가 있어야 한다.
- 툴에 이미지를 끌어다 놓는다 (편함)
- 파일 이름을 포트 이름으로 바꿔 폴더에 넣는다 (툴 없이)

둘째가 되기 때문에 첫째가 편의로 느껴진다.
**툴에서만 되는 기능을 만들면 툴이 유일한 통로가 되고, 툴이 막히는 날 작업이 막힌다.**

> **VnTool 적용**: 마스터 플랜 §0의 "진실은 순수 텍스트"가 같은 원칙이다.
> .yarn/CSV가 산출물이고 사람이 열어 읽을 수 있으므로, VnTool이 없어도 작업이 이어진다.
> 이 성질을 깨는 기능(툴 전용 바이너리 상태, 툴만 아는 암묵 규칙)을 추가하지 말 것.

### 2.3 툴이 추측하게 하지 마라

"비슷한 이름을 찾아 자동 연결" 같은 기능은 편해 보이지만,
규칙을 **"이름이 같으면 연결된다"에서 "툴이 알아서 해준다"로 바꾼다.**

그 순간 착각이 마법이 되고, 툴이 없는 자리에서 사람이 무엇을 해야 하는지 모르게 된다.
디버깅도 "왜 연결됐지"를 물어야 하는 문제로 바뀐다.

편의는 **사람이 할 일을 대신 해주는 것**이지 **규칙을 바꾸는 것**이 아니다.
이름을 바꿔서 복사해주는 건 전자다. 이름이 달라도 연결해주는 건 후자다.

### 2.4 규약의 사본을 만들지 마라

런타임과 툴이 같은 규약을 각자 구현하면, 규약이 바뀌는 날 **양쪽 다 오류 없이 어긋난다.**
런타임은 새 규칙으로 찾고 툴은 옛 규칙으로 그리는데, 둘 다 정상 동작한다고 믿는다.

착각을 편의로 쓰는 설계에서 이게 가장 위험한 실패다 — 툴이 거짓말을 시작하는데 아무도 모른다.

런타임 쪽은 `_Image` 판정과 `ui/{theme}/{portId}` 조립이 두 파일에 흩어져 있고
에디터 툴이 생기면 세 번째 사본이 된다. 그래서 사양서의 첫 작업이 규약 통합이다.

> **VnTool 적용**: 계약서(`runtime-contract.md`)의 규칙들이 같은 위험을 안고 있다.
> 예산 B(Pres 라인 수 계산), C1(`#line:` 태그) 같은 규칙은 런타임 코드와 이미터에 각각 존재한다.
> 이건 저장소가 달라 물리적 통합이 불가능하므로, **테스트로 고정**하는 게 유일한 방어다.
> 계약서가 "이미터 검증 단계에서 잡아야 한다"고 쓴 이유가 이것이다.

### 2.5 툴의 가치는 침묵을 화면으로 바꾸는 데 있다

이 코드베이스의 실패는 **대부분 예외가 아니라 침묵**이다. 실제로 확인된 것들:

| 침묵하는 실패 | 위치 | 증상 |
|---|---|---|
| 스프라이트 결손 시 로그 없이 건너뜀 | `UISpritePatcher.Apply` — `if(성공){...continue;}` 뒤에 else 없음 | 테마 전환 시 일부만 안 바뀜 |
| GameObject 바인딩 실패 경고가 주석 처리 | `UIBase.cs:179` | 참조가 null인 채로 런타임까지 감 |
| `Enum.TryParse` 결과 미검사 | `box_named` 처리 | 오타 시 조용히 `Portrait`(0)로 |
| `#line:` 태그 누락 | 계약서 C1 | 대사창 없이 빨리감기 + 입력 거부 (silent hang) |
| jump 시 서브 레인 미정리 | 계약서 A5 | 이후 노드에서 연출이 한 칸씩 계속 어긋남 |

**툴이 만드는 가치의 대부분이 여기서 나온다.**
새 기능을 더하는 게 아니라, 이미 일어나고 있는데 안 보이는 것을 보이게 만드는 것.

툴 기능을 설계할 때 "무엇을 더 할 수 있게 할까"보다
**"지금 무엇이 조용히 어긋나고 있나"**를 먼저 묻는 게 수확이 크다.

## 3. VnTool에 직접 옮겨지는 것

### 3.1 라인 경계가 곧 상태 경계다

커맨드 레퍼런스 §0.1:

> 한 대사 라인 앞에 붙인 커맨드들은 개별적으로 순차 실행되지 않고, **모여서 하나의 배치로 재생**된다.
> 따라서 커맨드 나열 순서는 "타임라인 순서"가 아니라 "셋업 → 배치" 논리 순서다.

이 성질이 세 가지를 한꺼번에 정당화한다.

1. **타임라인이 아니라 LineId 목록**이 맞다 — 라인 안쪽은 배치라 접을 게 없다
2. **시간 개념을 나중으로 미룰 수 있다** — 라인 경계의 확정 상태는 시간과 무관하다
3. **특정 LineId 즉시 재생**이 자연스럽다 — 처음부터 그 라인까지 접기만 하면 된다

### 3.2 Yarn 커맨드 텍스트 수준에서 접으면 매크로 확장표가 필요 없다

계약서 E4가 `show`→4스펙, `cast`→4, `emoji`→6 같은 1:N 확장표를 요구하는데,
그건 **스펙 수준에서 접을 때** 이야기다.

`cast c1 bandi a 3`을 인자 4개짜리 커맨드 하나로 읽으면 확장표가 불필요하다.
커맨드 레퍼런스가 이미 그 수준으로 쓰여 있고, 툴이 보는 것도 그 수준이다.

**결과: 최소 미리보기는 런타임의 StageState 리듀서(U13)에 의존하지 않는다.**

### 3.3 최소 미리보기에 필요한 커맨드는 200개 중 20개쯤

"무슨 배경에 누가 있고 뭐라고 말하는가"만 보려면:

| 갈래 | 커맨드 | 접을 상태 |
|---|---|---|
| 배경 | `bg_spawn` `bg_sprite` `bg_slot00/01/02` | `rigKey → (spriteKey, stage, layer)` |
| 슬롯 | `slot` `slot00/01/02` `slot_tyrant` | `slotKey → (stage, layer)` |
| 캐스팅 | `cast` `pose` `face` `actor` | `slotKey → (character, variant, emotion)`, `@alias → slotKey` |
| 표시 | `show` `fade_in` `fade_out` | `slotKey → visible` |
| 표정 | `face_swap` `face_crossfade` `mirror` | 위 갱신, `mirrored` |
| 대사창 | `box_named` `box_protagonist` `box_reset` | 박스 종류 |

나머지 180개(`place` `size` `move` `shot` `tx_*` `screen_*` `emoji_*` `idle_*` `char_visual_*`)는
**위치·크기·효과**만 건드린다. 무시해도 위 질문의 답은 정확하다.

### 3.4 커버리지가 보이는 리듀서

연출 정확도로 확장할 것이 확정돼 있으므로, **미처리 커맨드를 조용히 버리지 않는다.**
"인식했으나 아직 모델링 안 함"으로 기록해서, 라인 선택 시
"이 라인에 반영되지 않은 연출 3개"가 보이게 한다.

- 보이면 → 확장이 한 커맨드씩 늘어나는 작업이 된다
- 안 보이면 → 나중에 "왜 이 장면만 다르지"로 돌아온다

§2.5의 원칙을 툴 자신에게 적용하는 것이다.

### 3.5 에셋 파이프라인은 두 종류다

| 종류 | 예 | 툴이 필요한 것 |
|---|---|---|
| **문자열 규약형** | 배경 — `Resources.Load<Sprite>($"Backgrounds/{key}")` | **매니페스트 불필요.** 파일만 복사하면 이름으로 찾는다 |
| **키 매핑형** | 초상화 — `(characterId, variantSuffix, emotionKey)` → Sprite | 매핑 덤프 필요 |

초상화 쪽은 이미 준비돼 있다. `PortraitGeneratedDbSo.Entry`가
`characterId` / `variantKey` / `emotionKey` / `assetPath`를 들고 있다.
`assetPath`는 "디버깅용"이라 적혀 있지만 **내보내기가 요구하는 바로 그 값**이다.
내보내기 작업이 이 SO를 JSON으로 덤프하는 것으로 끝난다.

무대 위 캐릭터와 대사창 얼굴이 **같은 스프라이트**를 쓴다
(`fade_in`의 타겟이 `CharacterPortraitSprite_Root`). DB 하나가 양쪽을 덮는다.

> 새 에셋 종류를 추가할 때 **규약형으로 만들 수 있으면 그렇게 하라.**
> 매니페스트가 없으면 매니페스트가 낡을 일도 없다.

## 4. 런타임에서 확인된 수치

`Assets/@Scripts` 572파일 / 78,215줄 기준.

- `UIBase<TRefs>` 파생: **31종**
- `_Image`로 끝나는 enum 항목: **91개**
  - 이 중 **19개는 비-UIBase** (`CharacterRigDefinition` 10, `ScreenEffectRigDefinition` 3,
    `OverlayRigDefinition` 2, `EpisodeNodeRefs` 2, `BackgroundRigDefinition` 2) — 포트가 아니다
  - 실제 스프라이트 포트: **약 72개**
- 코드가 직접 대입해 규약과 경합하는 포트: **3개**
- 커맨드 어휘: 명명 200개 + `1fr`~`48fr` 동적 별칭 48개

> `_Image` 접미사가 "테마 패치 대상"과 "이 참조는 Image다" 두 의미로 쓰이고 있다.
> 지금은 `GetSpritePortIds()`가 `UIBase<TRefs>`에만 있어 사고가 안 나지만,
> 리그 정의 중 하나가 `IUISpritePortProvider`가 되면 유령 포트 19개가 조용히 생긴다.
> **타입 기준으로 수집하면 자동으로 걸러진다** — 이름 기준으로 수집하면 안 된다.

## 5. 열린 항목

1. `Assets/Resources` 미확인 — 테마 폴더 구성과 실제 채움 현황을 아직 못 봤다.
2. `UIContext.LocaleId`가 존재하나 `MakeImagePath`가 쓰지 않는다.
   로케일별 이미지가 필요해지면 주소 규약이 3차원이 된다. **필요해질 때 정한다.**
3. `runtime-work-orders.md`(U1–U16)와 `runtime-refactor-direction.md`가
   마스터 플랜에서 참조되지만 디스크에 없다.
